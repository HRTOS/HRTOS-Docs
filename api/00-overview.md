# HRTOS 概述

## 系统简介

HRTOS（Hard Real-Time Operating System）是一款面向 8051 系列单片机的实时操作系统，致力于在有限的硬件资源下提供完整的多任务运行环境、实时调度机制、内核同步与通信能力，以及配套的开发文档和示例。

HRTOS 4.0 在既有内核基础上持续完善任务管理、调度与切换、中断处理、时间管理、资源同步和任务间通信等机制，面向需要在 8051 平台上构建结构化、可维护嵌入式软件的开发场景。

HRTOS 不仅关注内核本身，也重视系统的工程完整性。通过配套 API、技术文档、示例程序、驱动与通信功能，帮助开发者从底层硬件控制逐步构建具备多任务协作能力的应用系统。

### 设计目标

- **面向实时任务**：提供基于任务优先级的调度机制，并支持相应的任务切换与时间管理能力。
- **适配有限资源**：围绕 8051 的存储空间、寻址方式与处理器特性设计内核实现，兼顾功能完整性与资源占用。
- **完善任务协作**：提供任务管理、同步原语、消息传递和等待唤醒等机制，降低多任务应用的组织复杂度。
- **协调任务与中断**：提供内核中断处理机制及相应的任务协作接口，支持对响应时间敏感的嵌入式应用。
- **重视工程可维护性**：通过 API 文档、示例、驱动与通信模块，建立从内核到应用的配套开发体系。
- **持续维护与完善**：以稳定性、可理解性和长期可用性为目标，持续完善内核实现与配套资料。

### 适用场景

HRTOS 可用于具有相应硬件资源和实时需求的 8051 嵌入式项目，例如：

- 工业控制与设备状态管理
- 实时数据采集与处理
- 串行通信及通信协议实现
- 电机控制与多任务协同
- 传感器节点与嵌入式终端
- 需要任务调度、资源同步或消息传递的控制系统

实际适用性取决于具体芯片的 RAM、XDATA、程序存储空间、定时器、中断资源以及应用的时序要求。

## 系统架构

HRTOS 以 8051 内核运行机制为基础，将任务执行、调度决策、时间管理、中断处理与任务间协作组织为相互配合的功能模块。

### 内核组成

| 模块 | 主要职责 |
|---|---|
| 内核核心（Kernel） | 提供内核运行所需的基础机制与调度协作接口 |
| 任务管理（Task） | 管理任务状态、挂起与恢复、优先级及任务生命周期相关操作 |
| 任务调度（Scheduler） | 根据内核调度规则处理任务选择与任务切换 |
| 同步机制 | 提供信号量、互斥锁等任务协作机制 |
| 通信机制 | 提供消息队列、邮箱等任务间数据传递方式 |
| 统一等待（Wait） | 为相关等待操作提供统一的阻塞状态与唤醒处理接口 |
| 时间管理（Time） | 提供系统节拍、任务延时、时间转换与运行时间查询等能力 |
| 中断管理（Interrupt） | 配合中断处理、内核运行状态与任务调度 |
| 系统配置（Config） | 管理任务数量、资源容量和时间参数等编译配置 |

事件机制及其他扩展功能的具体能力，应以 HRTOS 4.0 对应的 API、实现代码和模块文档为准。

### 8051 平台适配

HRTOS 面向 8051 架构设计，内核实现需要考虑该架构的寄存器组织、存储空间划分、中断机制以及不同芯片的硬件差异。

在适配具体芯片时，应重点确认：

- 内部 RAM、位寻址空间及 XDATA 的容量与使用情况
- 程序存储空间和编译后代码占用
- 定时器、中断源及相关寄存器配置
- 编译器、存储模型与芯片运行模式
- 系统配置与目标硬件资源之间的匹配关系

不同 8051 芯片在存储资源、指令执行效率和外设配置方面存在差异。因此，具体资源需求、时序表现与功能支持范围应以目标芯片、编译配置和实际测试结果为准，不宜将某一测试平台的内存地址或资源占用直接视为所有平台的固定要求。

## 任务管理与调度

### 多任务运行

HRTOS 为应用程序提供任务管理与任务切换机制，使开发者能够将不同功能拆分为相对独立的任务，并通过调度、等待和通信机制协调任务之间的执行关系。

任务管理相关能力包括：

- 查询任务状态与当前任务信息
- 挂起与恢复任务
- 设置任务优先级
- 主动让出执行机会
- 处理任务退出与删除
- 通过等待、唤醒和延时机制协调任务执行

具体操作的有效条件、返回值及边界行为，以任务管理 API 文档和对应实现为准。

### 优先级与任务类型

HRTOS 的调度体系包含普通任务与高速任务等不同执行路径。系统通过相应的任务状态、调度条件和任务切换机制组织任务运行。

普通任务的优先级用于表达任务之间的执行优先关系。高速任务则具有独立的调度与切换处理特点，适用于对任务响应路径有更高要求的场景。

使用时需要区分以下概念：

- **任务优先级**：用于表达任务之间的调度优先关系。
- **任务类型**：决定任务使用的相应执行与切换路径。
- **时间片机制**：用于处理系统配置所涉及的节拍或调度时机。
- **中断优先级**：由处理器中断控制机制及具体中断配置决定，不应简单等同于普通任务优先级。

任务切换的实际耗时受处理器运行模式、晶振频率、编译器、切换路径和中断活动等因素影响。实时应用应结合目标硬件的测量数据评估响应能力。

### 任务状态

任务运行涉及就绪、运行、等待、挂起及退出或删除等状态。状态之间的转换由任务管理接口、等待唤醒机制和调度过程共同决定。

```text
                 ┌──────────────┐
                 │    就绪      │
                 └──────┬───────┘
                        │ 调度
                        ▼
                 ┌──────────────┐
                 │    运行      │
                 └───┬──────┬───┘
                     │      │
              等待或延时    │ 挂起
                     ▼      ▼
               ┌────────┐ ┌────────┐
               │ 等待中 │ │ 已挂起 │
               └───┬────┘ └───┬────┘
                   │           │
                 唤醒         恢复
                   └─────┬─────┘
                         ▼
                       就绪

             退出或删除可使任务进入
                 不再参与调度的状态
```

该图用于说明常见的任务状态关系，不代表每个 API 都允许任意状态转换。具体状态值、查询结果和转换条件应参阅任务管理模块文档。

## 同步与通信机制

HRTOS 提供多种任务协作方式，以适应资源共享、执行同步和数据传递等不同需求。

### 信号量

信号量用于任务同步及资源计数等场景。任务可以通过获取与释放操作协调执行顺序，具体行为取决于信号量实现和相关 API。

使用信号量时，应明确资源计数的含义、等待条件、超时处理，以及任务与中断之间的调用边界。

### 互斥锁

互斥锁用于协调多个任务对共享资源的访问，减少并发执行造成的数据冲突。

互斥锁的使用应遵循其所有权与释放规则。递归获取、优先级继承、超时行为及中断上下文限制等细节，应以当前版本的互斥锁实现为准，不能仅根据模块名称推断其支持范围。

### 消息队列

消息队列用于在任务之间传递数据，适用于生产者与消费者分离、任务解耦及异步处理等场景。

消息队列的容量、消息格式、发送与接收行为，以及队列满或空时的处理方式，由对应 API 与系统配置决定。

### 邮箱

邮箱用于任务之间的消息传递，适合数据量较小、交互方式相对简单的通信场景。

邮箱与消息队列的区别应从消息格式、存储方式、容量及 API 语义理解，具体行为以邮箱模块文档为准。

### 事件与统一等待

事件可用于表达某种状态变化或同步条件。统一等待机制则为相关内核操作提供等待状态记录与唤醒处理。

统一等待并不意味着所有内核对象都采用完全相同的数据结构，也不意味着不同模块具有相同的阻塞、超时和返回值语义。使用具体对象时，应查阅对应模块的 API 文档。

## 中断与任务协作

8051 应用通常需要通过中断处理定时事件、外部信号和通信收发等实时活动。HRTOS 的内核运行机制需要协调中断处理与任务调度，避免中断事件与任务状态更新之间出现不一致。

### 中断处理原则

- 在中断服务程序中优先完成必要的硬件状态处理。
- 对需要较长时间完成的工作，可根据系统接口设计交由任务处理。
- 严格遵循各 API 对中断上下文的调用限制。
- 评估临界区、嵌套中断及调度触发对响应时间的影响。
- 对涉及任务状态或共享资源的操作，确认其并发安全条件。

### 中断上下文 API

HRTOS 的部分模块可能提供专用于中断上下文的接口，例如带有 `_from_isr` 后缀的 API。此类接口的具体支持范围、允许执行的操作及唤醒行为，应以 HRTOS 4.0 的公开声明和实现为准。

不能仅凭函数名称认定所有通信与同步操作都可以在中断中调用，也不应假定中断中记录的状态一定会由某个统一后台流程自动处理。开发者应针对具体 API 核实调用约束。

## 时间管理

### 系统节拍

HRTOS 使用定时器相关机制提供系统时间基准与任务延时支持。当前配置和目标硬件决定实际节拍周期，系统时间精度也会受到时钟源、定时器计数方式、编译配置及中断执行情况等因素影响。

### 时间转换与运行时间

时间管理模块提供与系统节拍相关的转换和查询接口，包括：

- `os_ms_to_tick()`：将毫秒数转换为相应的 tick 数。
- `os_sec_to_tick()`：将秒数转换为相应的 tick 数。
- `os_tick_get()`：查询系统节拍计数。
- `os_uptime_ms()`：获取以毫秒表示的系统运行时间。

上述接口的取整规则、有效参数范围及精度，应以时间管理模块文档为准。tick 与毫秒之间的换算结果受实际节拍配置影响。

### 任务延时与忙等待

HRTOS 提供不同用途的延时方式：

- `os_delay()`：通过系统等待机制请求任务延时，适合需要让出处理器执行机会的任务场景。
- `os_delay_ms()`：通过忙等待方式实现延时，执行期间会消耗处理器时间，适合经过测量并确认满足要求的短时等待场景。

忙等待的实际时长受时钟频率、编译器优化及中断影响。对于具有严格时序要求的硬件操作，应使用目标硬件实测结果验证延时精度。

## 系统配置与资源管理

HRTOS 通过系统配置控制任务容量、资源对象数量、消息队列容量及时间参数等。配置项名称、默认值和有效范围应以当前 HRTOS 4.0 源码中的配置头文件为准。

配置系统时，应综合考虑：

- 目标芯片的内部 RAM 与 XDATA 容量
- 任务数量及每个任务所需的运行资源
- 内核控制结构与通信缓冲区的占用
- 系统节拍和延时参数
- 中断与任务并发执行时的资源使用情况
- 编译器存储模型及生成代码的实际占用

增加任务数量或通信资源容量可能带来额外的内存需求。对于资源有限的 8051 芯片，应在编译后检查内存使用报告，并在目标硬件上验证系统行为。

## 开发与验证

HRTOS 的工程使用不仅包括调用 API，还包括目标芯片配置、应用任务设计、硬件驱动适配和运行验证。

建议开发流程包括：

- 确认目标芯片及编译环境。
- 根据芯片资源选择合适的系统配置。
- 阅读对应模块的 API 文档。
- 从最小示例开始，逐步加入任务、同步与通信功能。
- 对关键任务的响应时间、任务切换耗时和定时精度进行实测。
- 对长时间运行、异常输入及资源边界情况进行验证。
- 在修改内核或配置后重新执行相关测试。

对于实时性要求较高的项目，应明确区分功能测试、压力测试、运行时间测量与严格的最坏执行时间分析。有限时长的测试能够提供实际运行证据，但不能单独证明所有输入和执行路径都满足严格的硬实时期限。
