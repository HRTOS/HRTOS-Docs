# 内核模块

## 模块简介

HRTOS 内核模块提供系统启动、任务注册、调度策略控制、任务资源回收、存储区访问、异常处理及空闲任务钩子等基础能力。

模块通过任务注册接口建立任务或中断处理入口，通过调度控制接口切换系统运行策略，并由 Idle 任务完成内核运行环境初始化、用户主程序初始化及任务清理工作。

内核模块同时提供 Slab 异常处理钩子和 Idle Hook，便于用户扩展系统异常处理与空闲阶段的后台行为。

## 设计目标

- 提供任务与中断处理入口的注册机制。
- 支持调度模式及 HRTOS/MyOS 调度策略切换。
- 管理任务运行栈空间的分配与回收。
- 提供 DATA 与 XDATA 存储区之间的单字节数据传送接口。
- 提供系统初始化、任务清理及空闲任务运行机制。
- 提供资源分配异常处理与 Idle Hook 扩展接口。

## 使用场景

- 在系统启动阶段注册任务及相关处理入口。
- 根据应用需求选择调度模式。
- 在系统初始化阶段完成用户配置。
- 在任务结束或被系统标记为死亡状态后回收任务资源。
- 在系统空闲阶段执行轻量级后台处理。
- 在 Slab 资源分配异常时执行用户定义的处理逻辑。

## 数据类型

本模块没有额外公开的结构体或枚举类型。

模块接口使用 `char`、`unsigned char`、`unsigned int`、`u8`、`u16` 及函数指针等类型。其中，`u8`、`u16` 为项目内部使用的类型别名。

## 宏定义

本模块没有在所提供的公开头文件中定义新的宏。

任务数量、调度级别、资源数量及任务栈区域等限制由内核配置和内部头文件中的相关定义决定。

## 调度器中断编号设置

### os_dispatch_select

**函数原型**

```c
char os_dispatch_select(unsigned char interrupt_id);
```

**功能说明**

设置内核调度器使用的中断编号，并将编号保存至内部变量 `OS_DISPATCH_ID`。

**参数说明**

| 参数 | 类型 | 说明 |
|---|---|---|
| `interrupt_id` | `unsigned char` | 调度器使用的中断编号，有效范围为 0～31 |

**返回值**

| 返回值 | 含义 |
|---|---|
| `1` | 设置成功 |
| `-1` | 中断编号超出有效范围 |

**调用示例**

```c
char result;

result = os_dispatch_select(2);

if (result == 1)
{
    /* 设置成功 */
}
```

**注意事项**

- 本函数设置的是调度器中断编号，不是选择或返回一个中断处理函数。
- 函数只检查编号是否大于 31，没有检查中断编号是否对应实际存在的硬件中断。
- 提供的实现没有执行临界区保护，因此并不能仅凭本函数认定其具备并发调用保护。

## 任务与中断入口注册

### os_task_create

**函数原型**

```c
char os_task_create(
    unsigned int addr,
    unsigned char id,
    unsigned char pr,
    unsigned char sd
);
```

**功能说明**

注册标准任务、高速任务或中断处理入口。函数根据优先级参数选择相应的注册路径；对于标准任务和高速任务，还会在用户栈空间区域中申请连续空闲块，并记录相应的栈指针、任务信息或上下文数据。

该函数执行的是注册与初始化工作，并不意味着调用后任务函数会立即运行。

**参数说明**

| 参数 | 类型 | 说明 |
|---|---|---|
| `addr` | `unsigned int` | 任务或处理函数入口地址 |
| `id` | `unsigned char` | 任务编号 |
| `pr` | `unsigned char` | 用于区分标准任务、高速任务及中断处理入口的优先级参数 |
| `sd` | `unsigned char` | 栈空间配置参数 |

**返回值**

| 返回值 | 含义 |
|---|---|
| `1` | 注册路径执行成功 |
| `-1` | 系统配置已锁定 |
| `-2` | 优先级参数超出允许范围 |
| `-3` | 任务编号超出允许范围 |
| `-4` | 入口地址为空 |
| `-5` | 标准任务的栈空间参数超出限制 |
| `-6` | 标准任务编号已注册 |
| `-7` | 高速任务的栈空间参数超出限制 |
| `-8` | 用户栈空间不足 |

**任务类型与参数限制**

按照当前提供的源码和配置定义，任务类型判断逻辑如下：

- 当 `pr < OS_SCHED_LEVEL_MAX - 2` 时，进入标准任务注册路径。
- 当 `OS_SCHED_LEVEL_MAX - 2 <= pr < OS_SCHED_LEVEL_MAX - 1` 时，进入高速任务注册路径。
- 当 `pr == OS_SCHED_LEVEL_MAX - 1` 时，设置中断处理入口地址。
- 当 `pr == OS_SCHED_LEVEL_MAX` 时，设置中断嵌套处理入口地址。
- 当 `pr > OS_SCHED_LEVEL_MAX` 时，返回 `-2`。

如果当前配置中的 `OS_SCHED_LEVEL_MAX` 为 10，则上述分支分别对应标准任务优先级参数 0～7、高速任务参数 8、中断处理入口参数 9 和中断嵌套处理入口参数 10。

标准任务的 `sd` 最大允许值为 6，高速任务的 `sd` 最大允许值为 25。源码会在申请栈空间前将 `sd` 加一，因此不能简单地将传入参数理解为最终分配的栈块数量。

**调用示例**

```c
char result;

/* 注册一个标准任务 */
result = os_task_create(
    (unsigned int)task_func,
    0,
    3,
    5
);

if (result == 1)
{
    /* 注册成功 */
}
```

上述示例假设 `task_func` 是有效的任务入口，并且任务编号、优先级、栈空间及系统配置均符合要求。

**注意事项**

- `OS_CFG_LOCK` 非零时，函数拒绝注册操作。
- 标准任务注册会检查重复编号；高速任务采用独立的高速任务存储与标记机制。
- 标准任务和高速任务使用位图管理的用户栈区域，并需要足够的连续空闲空间。
- 中断处理及中断嵌套处理分支在源码中通过标签直接写入入口地址，执行路径与标准任务注册不同，不应将标准任务的全部参数检查规则直接套用到这两个分支。
- 中断处理入口的具体注册方式及其与硬件中断向量的对应关系，需要结合中断初始化和分发代码确认。

## 调度模式切换

### os_scheduler_mode_switch

**函数原型**

```c
char os_scheduler_mode_switch(unsigned char id);
```

**功能说明**

切换 HRTOS 的调度模式。根据源码中的参数判断及内部变量操作：

- `id = 0`：切换至时间片模式，将 `OS_RTOS_YES` 置为 0，并保存当前 `OS_TIME_ONCE`。
- `id = 1`：切换至优先级模式，将 `OS_RTOS_YES` 置为 1，调整 `OS_TIME_XY`，再恢复保存的 `OS_TIME_ONCE`。

**参数说明**

| 参数 | 类型 | 说明 |
|---|---|---|
| `id` | `unsigned char` | `0` 表示时间片模式，`1` 表示优先级模式 |

**返回值**

| 返回值 | 含义 |
|---|---|
| `1` | 调度模式切换成功 |
| `-1` | 参数无效，或系统当前已处于指定模式 |

**调用示例**

```c
char result;

/* 切换至优先级模式 */
result = os_scheduler_mode_switch(1);

if (result == 1)
{
    /* 切换成功 */
}
```

**注意事项**

- 该接口修改调度模式相关状态和时间参数。
- 切换时会调整 `OS_TIME_ONCE` 与 `OS_TIME_XY`，因此时间参数的变化应结合系统计时实现理解。
- 源码没有在该函数内部使用临界区保护。
- 建议在应用明确的控制流程中进行模式切换，并验证切换前后的调度与计时行为。

## HRTOS/MyOS 调度策略切换

### os_set_scheduler

**函数原型**

```c
char os_set_scheduler(unsigned char id);
```

**功能说明**

通过修改 `OS_INTERRUPT_T0` 选择相应的调度策略，并在切换时保存或恢复 `OS_TIME_ONCE` 等时间参数。

根据当前实现：

- 当 `id == 0` 且 `OS_INTERRUPT_T0 == 0` 时，将 `OS_INTERRUPT_T0` 设为 1，并保存 `OS_TIME_ONCE`。
- 当 `id == 1` 且 `OS_INTERRUPT_T0 == 1` 时，将 `OS_INTERRUPT_T0` 设为 0，调整 `OS_TIME_XY`，并恢复保存的 `OS_TIME_ONCE`。
- 其他情况返回 `-1`。

**参数说明**

| 参数 | 类型 | 说明 |
|---|---|---|
| `id` | `unsigned char` | 调度策略切换标识，具体取值与 HRTOS/MyOS 的对应关系需统一确认 |

**返回值**

| 返回值 | 含义 |
|---|---|
| `1` | 状态切换成功 |
| `-1` | 参数不符合当前切换条件，或当前状态已不满足切换条件 |

**调用示例**

```c
char result;

result = os_set_scheduler(1);
```

调用前应先根据项目当前版本确认 `id` 与 HRTOS/MyOS 的对应关系。

**注意事项**

当前材料存在一处需要审核的定义不一致：

- 公开头文件注释写的是 `1 = HRTOS`、`0 = MYOS`。
- `scheduler_mode.c` 中的函数注释写的是 `0 = HRTOS`、`1 = MYOS`。
- 函数实际实现只体现 `OS_INTERRUPT_T0` 的状态转换，并未直接说明每种状态对应哪一个调度器。

因此，在确认 `OS_INTERRUPT_T0` 的初始化值及相关调度分发代码之前，文档不应武断地把参数值解释为某一确定的调度器名称。

该接口与 `os_scheduler_mode_switch()` 的用途不同：前者改变 HRTOS/MyOS 相关的调度策略状态，后者改变时间片模式与优先级模式。

## DATA 与 XDATA 数据传送

### os_data_to_xdata

**函数原型**

```c
void os_data_to_xdata(u8 addr, u16 addr2);
```

**功能说明**

读取 DATA 区指定地址的一个字节，并将该字节写入 XDATA 区的目标地址。

该函数通过汇编指令访问间接 DATA 地址及 XDATA 地址，适用于 8051 存储区之间的单字节传送。

**参数说明**

| 参数 | 类型 | 说明 |
|---|---|---|
| `addr` | `u8` | DATA 区源地址 |
| `addr2` | `u16` | XDATA 区目标地址 |

**返回值**

无。

**调用示例**

```c
os_data_to_xdata(src_addr, dst_addr);
```

其中，`src_addr` 和 `dst_addr` 应替换为符合实际存储区布局的地址值。

**注意事项**

- 该接口传送一个字节，不是通用的多字节内存复制函数。
- 函数执行期间直接设置 `EA = 0`，完成后直接设置 `EA = 1`。
- 实现并未保存并恢复调用前的中断使能状态，因此不能将其描述为严格恢复原中断状态。
- 应确认地址对应的存储区及访问范围有效。

### os_xdata_to_data

**函数原型**

```c
void os_xdata_to_data(u16 addr2, u8 addr);
```

**功能说明**

读取 XDATA 区指定地址的一个字节，并将其写入 DATA 区目标地址。

**参数说明**

| 参数 | 类型 | 说明 |
|---|---|---|
| `addr2` | `u16` | XDATA 区源地址 |
| `addr` | `u8` | DATA 区目标地址 |

**返回值**

无。

**调用示例**

```c
os_xdata_to_data(src_addr, dst_addr);
```

**注意事项**

- 该接口同样只传送一个字节。
- 函数通过 `MOVX` 读取 XDATA 数据，再通过间接寻址写入 DATA 区。
- 函数结束时直接设置 `EA = 1`，没有恢复调用前的中断状态。
- 对这两个接口的中断行为进行评估时，应考虑其调用环境以及是否可能在原本关闭中断的代码路径中被调用。

## 用户主程序入口

### hrtos_main

**函数原型**

```c
void hrtos_main();
```

**功能说明**

`hrtos_main()` 是 HRTOS 运行流程中的用户主程序初始化入口。

在 `os_idle_task()` 中，内核先完成任务和资源状态的初始化，然后调用 `hrtos_main()`。该函数执行完成后，内核将 `OS_CFG_LOCK` 置为 1，随后进入 Idle 循环。

**调用示例**

```c
void hrtos_main(void)
{
    /* 执行应用初始化 */

    /* 注册用户任务 */

    /* 完成其他启动配置 */
}
```

**注意事项**

- 应在该入口中完成应用所需的初始化与任务注册。
- 按当前 `os_idle_task()` 的实现，`hrtos_main()` 返回后配置锁会被启用。
- 不应假定系统进入该函数时已经完成所有用户配置。
- 用户任务和其他配置项应按照 HRTOS 的启动要求，在配置锁启用前完成注册。

## 任务资源清理

### os_task_cleanup

**函数原型**

```c
char os_task_cleanup(unsigned char id);
```

**功能说明**

清理指定任务的栈空间占用标记、任务上下文及相关等待状态。对于高速任务，还会清理相应的高速任务注册标记和上下文数据。

函数同时遍历系统资源，清除该任务在等待位图中的记录，并释放其作为 `owner` 持有的资源所有权标记。

**参数说明**

| 参数 | 类型 | 说明 |
|---|---|---|
| `id` | `unsigned char` | 待清理的任务编号 |

**返回值**

| 返回值 | 含义 |
|---|---|
| `1` | 清理成功 |
| `-1` | 任务编号无效，或对应的任务栈记录不存在 |

**调用示例**

```c
char result;

/* 示例：清理任务 1 */
result = os_task_cleanup(1);
```

是否适合由应用直接调用，应结合任务生命周期管理流程决定。

**清理过程**

函数主要执行以下操作：

- 检查任务编号及对应的任务栈记录。
- 根据标准任务或高速任务类型计算需要回收的栈空间范围。
- 清除对应的任务注册记录和上下文数据。
- 清除高速任务的时间等待标记（适用于高速任务）。
- 清除该任务在系统资源等待位图中的记录，并递减相应的等待计数。
- 如果该任务是某项资源的 `owner`，则将资源所有者标记设为 `OS_INVALID_ID`。
- 清理任务控制块中的等待类型、等待标志、等待对象和等待时间。
- 将任务状态设置为 `READY`，恢复 `OS_HRTOS` 的原值后返回。

**注意事项**

- 任务编号 0 不允许清理。
- 当前实现允许的最大任务编号为 `OS_PROCESS_MAX + 1`。
- 标准任务和高速任务采用不同的栈空间及上下文记录。
- 源码中的注释提到“删除态”，但实际赋值为 `OS_TASK[id].state = READY`，因此文档应以实际赋值为准。
- 清理函数自身没有在入口处关闭中断；当前 `os_idle_task()` 在执行清理扫描时会先关闭中断。若在其他上下文调用，需要另行核对并发保护条件。
- 释放 `owner` 标记不等同于已完成所有可能的资源交接处理。若资源等待和所有权交接存在更复杂的约束，需要结合资源模块源码继续验证。

## Idle 任务与空闲钩子

### os_idle_task

**函数原型**

```c
void os_idle_task(void);
```

**功能说明**

`os_idle_task()` 是内核的空闲任务入口，负责初始化任务控制块和系统资源状态、执行用户主程序初始化，以及在系统运行期间处理任务清理请求和调用 Idle Hook。

**初始化阶段**

函数首先关闭中断，并执行以下操作：

- 清空 Idle Hook 和 Slab 异常处理钩子指针。
- 清除调度请求状态。
- 将 `OS_CFG_LOCK` 设置为 0，允许注册配置项。
- 初始化标准任务的等待类型、状态、等待时间和等待对象。
- 清空高速任务等待标记。
- 初始化系统资源的值、所有者、等待计数、等待位图和待处理信号状态。
- 调用 `hrtos_main()` 执行用户主程序初始化。

`hrtos_main()` 返回后，函数将 `OS_CFG_LOCK` 设置为 1，并重新开启中断。

**运行阶段**

随后进入永久循环，持续执行以下操作：

- 临时关闭中断，扫描标准任务编号 1 至 `OS_PROCESS_MAX - 1`。
- 对状态为 `DEAD` 的任务调用 `os_task_cleanup()`。
- 根据高速任务删除标记，清理对应的高速任务。
- 清除已经处理的高速任务删除标记。
- 重新开启中断。
- 如果已注册 Idle Hook，则调用该钩子函数。

**注意事项**

- Idle 任务的初始化过程是系统启动流程的重要组成部分。
- 当前实现只扫描标准任务编号 1 至 `OS_PROCESS_MAX - 1`，并不在该循环中扫描编号 0。
- Idle Hook 在永久循环中被反复调用，不应将其当作只执行一次的初始化回调。
- Idle Hook 应保持短小，并避免长时间阻塞，否则会影响 Idle 阶段的其他处理。
- 低功耗操作是否适合放入 Idle Hook，需要结合具体芯片的中断唤醒机制和系统运行要求评估。

### os_idle_hook_register

**函数原型**

```c
void os_idle_hook_register(void (*hook)(void));
```

**功能说明**

注册 Idle Hook。当系统进入 `os_idle_task()` 的循环并执行到钩子调用位置时，内核会调用已注册的函数。

传入空指针可取消已注册的钩子。

**参数说明**

| 参数 | 类型 | 说明 |
|---|---|---|
| `hook` | `void (*)(void)` | Idle Hook 函数指针 |

**返回值**

无。

**调用示例**

```c
void my_idle_hook(void)
{
    /* 执行轻量级后台处理 */
}

void hrtos_main(void)
{
    os_idle_hook_register(my_idle_hook);

    /* 其他系统初始化 */
}
```

取消钩子时可传入空指针：

```c
os_idle_hook_register(0);
```

**注意事项**

- Idle Hook 可能被频繁调用，应避免长时间执行。
- 不宜在钩子中执行阻塞式等待，否则可能导致 Idle 循环无法继续。
- 如果钩子用于低功耗管理，应确认不会影响中断响应及任务唤醒。
- 注册接口本身没有显示的临界区保护；若存在其他上下文同时修改钩子指针，应审查其同步要求。

## Slab 异常处理

### os_slab_overflow

**函数原型**


**功能说明**

处理 Slab 资源分配异常。函数首先检查 `g_slab_overflow_hook` 是否已注册：

- 已注册钩子时，调用用户提供的异常处理函数。
- 未注册钩子时，进入无限循环。

因此，当前源码中的默认处理行为是停留在循环中，而不是主动执行系统复位。

**调用示例**

该函数通常由系统内部在相应异常路径中调用，应用一般不需要主动调用。

**注意事项**

- 异常钩子应尽可能简洁，并考虑发生异常时系统状态是否仍然可靠。
- 如果希望异常后复位或进入特定安全状态，应由用户处理函数显式实现。
- 应结合 Slab 分配相关源码确认触发该处理函数的具体条件。

## 使用建议

- **启动配置：** 在配置锁启用前完成任务注册及其他初始化工作。
- **调度策略：** 区分调度模式切换与 HRTOS/MyOS 策略切换，调用前确认参数定义。
- **任务栈：** 根据任务类型合理设置栈空间参数，并确认用户栈区域有足够的连续空闲块。
- **任务清理：** 通过系统既定的生命周期流程处理任务回收，避免在不明确的上下文中直接调用清理接口。
- **异常处理：** 根据产品需求注册 Slab 异常钩子，并明确异常发生后的预期行为。
- **Idle Hook：** 仅执行适合空闲上下文的轻量级处理，并验证低功耗操作与中断唤醒的兼容性。
- **存储区访问：** 使用 DATA/XDATA 传送接口时，确认地址空间和中断状态管理符合应用要求。
