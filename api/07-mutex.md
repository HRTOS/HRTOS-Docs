# 互斥锁模块

## 模块简介

互斥锁模块用于协调多个任务对共享资源的访问，采用统一资源模型记录互斥锁的拥有者、等待任务及等待状态。

模块提供互斥锁初始化、获取和释放接口。获取已被其他任务持有的互斥锁时，当前任务通过 `os_wait()` 进入等待流程；实现还包含优先级继承逻辑，尝试提高锁拥有者的当前优先级，降低高优先级任务因低优先级任务持锁而受到的阻塞。

当前实现不支持递归获取同一把互斥锁。

## 设计目标

- 为共享资源提供互斥访问机制。
- 通过资源拥有者标识记录锁的持有关系。
- 支持等待任务管理与锁释放后的任务唤醒。
- 在发生锁竞争时尝试实施优先级继承。

## 使用场景

- 保护多个任务共同访问的共享数据。
- 协调对共享硬件资源的访问。
- 保护需要互斥执行的临界代码。
- 管理任务之间存在竞争关系的资源。

## 数据类型

本模块使用 `hrtos_internal.h` 中定义的 `OS_RESOURCE` 结构，通过 `OS_RES[mid]` 访问互斥锁对应的资源槽位。

主要使用以下成员：

| 成员 | 功能说明 |
|---|---|
| `value` | 初始化时设为 `1`，但当前锁获取和释放逻辑主要依据 `owner` 判断锁状态 |
| `owner` | 当前互斥锁拥有者的任务 ID；`OS_INVALID_ID` 表示没有拥有者 |
| `wait_mask` | 等待该资源的任务位图 |
| `wait_cnt` | 等待任务计数，初始化时清零 |

任务优先级相关字段：

| 字段 | 功能说明 |
|---|---|
| `base_prio` | 任务基础优先级 |
| `cur_prio` | 任务当前优先级，可在锁竞争时被调整 |

互斥锁的获取和释放逻辑会同时操作任务优先级字段与 `OS_PROCESS_OK` 中的优先级编码。其编码方式及调度效果应以系统任务创建和调度代码为准。

## 宏定义

本模块没有在公开头文件中定义专用宏。

## API 函数列表

| 函数名称 | 功能说明 |
|---|---|
| `os_mutex_init()` | 初始化互斥锁资源 |
| `os_mutex_lock()` | 获取互斥锁，必要时进入等待流程 |
| `os_mutex_unlock()` | 释放互斥锁，并在存在等待任务时尝试转移所有权 |

## API 详细说明

### os_mutex_init

函数原型：

```c
char os_mutex_init(u8 mid);
```

参数说明：

| 参数 | 类型 | 说明 |
|---|---|---|
| `mid` | `u8` | 互斥锁对应的资源槽位编号 |

返回值：

| 返回值 | 说明 |
|---|---|
| `1` | 初始化成功 |
| `-1` | 资源槽位编号无效 |

功能说明：

初始化指定的互斥锁资源。函数将资源的 `value` 设置为 `1`，将 `owner` 设置为 `OS_INVALID_ID`，并清空等待位图与等待计数。

调用示例：

```c
char result;

result = os_mutex_init(0);

if (result == 1)
{
    /* 初始化成功 */
}
```

注意事项：

- `mid` 必须小于 `OS_RESOURCE_MAX`。
- 应在系统启动阶段或能够确保资源未被并发使用的环境中初始化。
- 该函数会覆盖拥有者和等待状态，不应在互斥锁正在使用时重新初始化。
- 当前实现没有关闭总中断或采用其他显式同步措施，初始化时应确保不存在并发访问。
- 函数形参在实现中声明为 `char`，公开头文件中声明为 `u8`。建议统一两处声明与定义的类型，避免接口声明不一致。

### os_mutex_lock

函数原型：

```c
char os_mutex_lock(u8 mid);
```

参数说明：

| 参数 | 类型 | 说明 |
|---|---|---|
| `mid` | `u8` | 互斥锁对应的资源槽位编号 |

返回值：

| 返回值 | 说明 |
|---|---|
| `1` | 当前任务直接获取锁 |
| `-1` | 编号无效，或当前任务已经持有该锁 |
| 其他值 | 锁被占用时，返回 `os_wait()` 的结果 |

功能说明：

尝试获取指定互斥锁。函数首先检查资源编号，然后读取当前任务 ID，并关闭总中断进入临界区。

**互斥锁已由当前任务持有时**

函数恢复总中断并返回 `-1`，因此当前实现不支持递归获取。

**互斥锁没有拥有者时**

函数将当前任务 ID 写入 `owner`，根据 `OS_PROCESS_OK` 中的优先级编码重新设置当前任务的 `base_prio` 和 `cur_prio`，恢复总中断后返回 `1`。

**互斥锁已由其他任务持有时**

函数根据当前任务的基础优先级和锁拥有者的当前优先级执行优先级比较。如果等待任务的基础优先级高于锁拥有者的当前优先级，则提高拥有者的 `cur_prio`，并尝试同步更新 `OS_PROCESS_OK` 中的优先级编码。

完成上述处理后，函数恢复总中断，并调用：

```c
os_wait(WAIT_MUTEX, mid, 0);
```

该调用将互斥锁等待交由内核等待机制处理，函数最终返回 `os_wait()` 的返回值。

调用示例：

```c
char result;

result = os_mutex_lock(0);

if (result == 1)
{
    /* 当前调用直接获取锁 */
    /* 访问受保护的共享资源 */

    os_mutex_unlock(0);
}
```

注意事项：

- 返回 `1` 在当前实现中明确对应直接获取锁的路径。锁竞争路径返回的是 `os_wait()` 的结果，不能仅根据返回值为非零就断言当前任务已经获得互斥锁。
- 锁竞争时的优先级提升发生在调用 `os_wait()` 之前。
- 当前实现没有在 `os_mutex_lock()` 内部循环重试获取锁，也没有在等待返回后自行验证当前任务是否已经成为锁拥有者。
- 优先级继承逻辑只比较当前等待任务与锁拥有者的优先级；多个锁、多个等待者之间的完整继承与恢复策略，还需要结合其他内核代码确认。
- 函数直接设置 `EA = 0` 和 `EA = 1`，没有保存并恢复调用前的总中断使能状态。

### os_mutex_unlock

函数原型：

```c
char os_mutex_unlock(u8 mid);
```

参数说明：

| 参数 | 类型 | 说明 |
|---|---|---|
| `mid` | `u8` | 互斥锁对应的资源槽位编号 |

返回值：

| 返回值 | 说明 |
|---|---|
| `1` | 所有权已转移给选中的等待任务，并调用唤醒接口 |
| `0` | 释放流程完成，未保留有效的等待任务所有权 |
| `-1` | 编号无效，或当前任务不是锁拥有者 |

功能说明：

释放指定互斥锁。调用时，函数首先检查编号，然后确认当前任务是否为锁拥有者。非拥有者调用时返回 `-1`。

验证拥有者身份后，函数将当前任务的 `cur_prio` 恢复为 `base_prio`，并同步更新 `OS_PROCESS_OK` 中的优先级编码。

**存在等待任务时**

函数遍历 `wait_mask` 中的任务位，选择 `OS_TASK[i].cur_prio` 最高的任务。选定任务后，将互斥锁的 `owner` 设置为该任务 ID，并调用：

```c
wake_task(next, WAIT_SIGNAL);
```

随后恢复总中断并返回 `1`。

如果等待位图非零，但遍历后没有选出有效任务，函数会清空 `wait_mask`、将 `owner` 设为 `OS_INVALID_ID`，恢复总中断并返回 `0`。

**没有等待任务时**

函数将 `owner` 设置为 `OS_INVALID_ID`，恢复总中断并返回 `0`。

调用示例：

```c
char result;

result = os_mutex_unlock(0);

if (result == 1)
{
    /* 锁所有权已转移，并调用了等待任务唤醒接口 */
}
else if (result == 0)
{
    /* 释放流程完成，未转移给有效等待任务 */
}
```

注意事项：

- 只有当前锁拥有者才能释放互斥锁。
- 当前实现会在释放时恢复当前任务的基础优先级。
- 选定等待任务后，函数先更新 `owner`，再调用 `wake_task()`。因此，所有权转移和任务唤醒的实际配合效果需要结合 `os_wait()` 与 `wake_task()` 的实现验证。
- 选择等待任务时，代码遍历范围为 `0` 到 `OS_PROCESS_MAX - 1`，并依据 `cur_prio` 选择最高优先级任务；当多个任务优先级相同时，优先选择编号较小的任务。
- 函数没有在释放时显式验证候选任务当前是否仍处于 `WAIT_MUTEX` 状态，而是依赖 `wait_mask` 的正确性。
- 函数直接设置 `EA = 0` 和 `EA = 1`，没有保存并恢复调用前的总中断使能状态。

## 使用建议

- 在系统启动阶段完成互斥锁初始化，并避免在运行过程中重复初始化正在使用的锁。
- 获取锁后应尽量缩短持锁时间，避免长时间占用共享资源。
- 对锁竞争路径，应根据实际 `os_wait()` 返回约定编写调用逻辑，不应将任意非零返回值都视为获取锁成功。
- 只有成功持有互斥锁的任务才应调用释放接口。
- 多把锁共同使用时，应在应用层规划统一的加锁顺序，降低循环等待风险。
- 对实时性要求较高的任务，应评估锁竞争导致的阻塞时间，以及优先级继承与恢复策略的实际效果。


## 使用说明

- **锁的使用**：互斥锁用于协调多个任务对共享资源的访问。访问共享资源前应获取互斥锁，并在使用完成后及时释放。
- **任务所有权**：互斥锁具有任务所有权约束，应由持有该锁的任务执行正常释放操作，避免错误释放或破坏锁状态。
- **竞争与等待**：当互斥锁已被其他任务持有时，后续任务的处理行为应遵循接口规定的等待机制。使用时应结合任务调度与等待唤醒机制理解接口返回结果。
- **优先级继承**：优先级继承用于缓解优先级反转。使用互斥锁时，应注意任务优先级可能随锁竞争发生变化，不应假定任务优先级在运行期间始终保持不变。
- **多锁场景**：当任务同时持有多个互斥锁时，应合理安排加锁与解锁顺序，并避免形成循环等待。
- **中断与临界区**：互斥锁主要用于任务间同步，不应默认其接口可在中断服务程序中安全调用。相关操作应遵循系统统一的中断管理约定。
