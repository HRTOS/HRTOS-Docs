# 中断管理模块

## 模块简介

HRTOS 中断管理模块提供中断编号查询、临界区保护、运行环境判断、中断触发调度，以及中断上下文与任务之间的通信接口。

模块通过临界区嵌套计数和中断状态保存机制管理临界区，通过调度请求标志及资源状态记录，支持中断环境下的邮箱、事件、信号量和消息队列操作。

模块主要包含以下功能：

- **中断识别**：获取当前中断编号，判断代码是否运行在中断环境。
- **临界区保护**：进入临界区时保存原有中断使能状态，并在适当时机恢复。
- **调度请求**：设置调度请求标志，必要时触发 Timer0 中断。
- **中断通信**：提供邮箱、事件、信号量和消息队列的中断发送或释放接口。

## 设计与使用场景

中断管理模块适用于以下场景：

- 在共享数据访问期间保护关键代码。
- 在中断服务程序中识别当前中断来源。
- 在中断中通知任务处理新数据或事件。
- 在中断中发送消息队列数据。
- 在需要系统重新检查调度条件时提交调度请求。

需要注意，中断上下文中的接口不应执行阻塞等待。具体接口是否可以安全用于所有中断场景，还取决于中断嵌套方式、共享资源访问规则和内核调度实现。

## 相关宏与内部状态

### 临界区宏

| 宏或接口 | 功能 |
|---|---|
| `OS_ENTER_CRITICAL()` | 进入临界区，具体展开行为取决于宏定义 |
| `OS_EXIT_CRITICAL()` | 退出临界区，具体展开行为取决于宏定义 |
| `os_enter_critical()` | 进入临界区并管理嵌套计数 |
| `os_exit_critical()` | 退出临界区，并在嵌套计数归零时恢复保存的中断状态 |

本文所提供的实现直接展示了 `os_enter_critical()` 和 `os_exit_critical()` 的行为。宏是否直接映射到这两个函数，应以实际配置文件中的定义为准。

### 相关内部状态

| 状态 | 功能 |
|---|---|
| `EA` | 8051 全局中断使能控制位 |
| `os_critical_nesting` | 临界区嵌套计数 |
| `os_int_status` | 保存进入最外层临界区前的中断使能状态 |
| `OS_INTERRUPT_PROTECT` | `os_interrupt_id()` 返回的中断编号状态 |
| `OS_ISR_FLAG` | `os_in_isr()` 查询的中断环境标志 |
| `OS_SCHED_REASON` | 调度请求标志 |
| `TF0` | Timer0 溢出标志；`os_schedule_request()` 通过设置该标志触发 Timer0 中断处理 |

| `os_enter_critical()` | 进入临界区 |

| `os_in_isr()` | 判断当前是否处于中断环境 |

| `os_msgq_send_from_isr()` | 在中断环境向消息队列发送一个字节 |

## API 详细说明

### os_interrupt_id

**函数原型**

```c
char os_interrupt_id();
```

**参数**

无。

**返回值**

返回 `OS_INTERRUPT_PROTECT` 的当前值。接口注释约定中断编号为 `0`、`2～31`，并按照自然中断入口顺序排列。

**功能说明**

查询当前中断编号。实现本身只返回内部状态 `OS_INTERRUPT_PROTECT`，并不在该函数中计算或转换中断向量编号。

**调用示例**

```c
char irq_id = os_interrupt_id();
```

**注意事项**

- 该接口适合在需要识别中断来源的代码中使用。
- 编号与具体中断入口的对应关系，应结合中断入口配置及内核实现确认。
- 如果在任务上下文中调用，其返回值是否具有有效的中断来源含义，不能仅凭该函数实现确定。

### os_enter_critical

**函数原型**

```c
void os_enter_critical();
```

**参数与返回值**

无参数，无返回值。

**功能说明**

进入临界区，通过嵌套计数支持多层临界区调用。

当 `os_critical_nesting == 0` 时，函数首先保存当前 `EA` 状态到 `os_int_status`，然后将 `EA` 置零。之后每次调用均增加嵌套计数。

其核心逻辑如下：

```c
if (os_critical_nesting == 0)
{
    os_int_status = EA;
    EA = 0;
}

os_critical_nesting++;
```

**调用示例**

```c
os_enter_critical();

/* 受保护的关键操作 */

os_exit_critical();
```

**注意事项**

- 每次进入临界区，都必须与对应的 `os_exit_critical()` 配对。
- 临界区支持嵌套；只有最外层进入时才保存中断状态并关闭全局中断。
- 临界区内的操作应尽量简短，以控制中断屏蔽时间。
- 不要在未核实配对关系的情况下随意调用退出接口。

### os_exit_critical

**函数原型**

```c
void os_exit_critical();
```

**参数与返回值**

无参数，无返回值。

**功能说明**

退出临界区，减少嵌套计数。当 `os_critical_nesting > 0` 时，函数才会执行减计数操作；当计数减至零时，将 `EA` 恢复为 `os_int_status` 保存的状态。

核心逻辑如下：

```c
if (os_critical_nesting > 0)
{
    os_critical_nesting--;

    if (os_critical_nesting == 0)
    {
        EA = os_int_status;
    }
}
```

如果嵌套计数已经为零，调用不会执行任何操作。

**注意事项**

- 应与 `os_enter_critical()` 配对使用。
- 只有退出最外层临界区时才恢复保存的中断状态。
- 恢复的是进入最外层临界区之前的状态，而不是无条件打开中断。
- 不正确的配对可能破坏后续临界区的保护行为。

### os_in_isr

**函数原型**

```c
char os_in_isr(void);
```

**参数**

无。

**返回值**

| 返回值 | 含义 |
|---|---|
| `1` | `OS_ISR_FLAG` 当前为非零，即系统标志指示处于中断环境 |
| `0` | `OS_ISR_FLAG` 当前为零，即系统标志指示处于任务环境 |

**功能说明**

查询内核维护的中断环境标志：

```c
char os_in_isr(void)
{
    return OS_ISR_FLAG;
}
```

该函数本身不检测硬件中断状态，而是直接返回内核标志。

**调用示例**

```c
if (os_in_isr())
{
    /* 中断环境下的处理 */
}
else
{
    /* 任务环境下的处理 */
}
```

**注意事项**

- 返回结果依赖于内核对 `OS_ISR_FLAG` 的维护。
- 不应仅凭该函数就推断所有中断嵌套场景下的行为；相关标志更新时机应结合内核中断入口与退出代码确认。

### os_queue_send_from_isr

**函数原型**

```c
char os_queue_send_from_isr(u8 id, u8 _data);
```

**参数**

| 参数 | 类型 | 说明 |
|---|---|---|
| `id` | `u8` | 资源槽位编号 |
| `_data` | `u8` | 待写入的数据 |

**返回值**

| 返回值 | 含义 |
|---|---|
| `1` | 写入成功 |
| `-1` | 资源编号无效 |

**功能说明**

该接口检查资源编号后，直接更新对应资源的 `value`，增加 `pending_signal`，并设置调度请求标志。

核心操作如下：

```c
OS_RES[id].value = _data;
OS_RES[id].pending_signal++;
OS_SCHED_REASON = 1;
```

该实现不会在函数内部遍历等待任务，也不会直接调用任务唤醒函数。

**调用示例**

```c
char result = os_queue_send_from_isr(0, 0x55);
```

**注意事项**

- 资源编号必须小于 `OS_RESOURCE_MAX`。
- 接口实际操作的是 `OS_RES[id]` 资源槽位；数据以单个字节形式写入。
- 连续调用会覆盖 `value`，同时分别增加 `pending_signal`。因此，不能将该接口直接视为能够保存任意数量消息的 FIFO 邮箱。
- 函数没有自行关闭全局中断，也没有调用 `os_schedule_request()`。
- 数据写入和调度标志设置后的具体任务唤醒行为，取决于内核对 `pending_signal` 和 `OS_SCHED_REASON` 的处理。

### os_schedule_request

**函数原型**

```c
char os_schedule_request(char id);
```

**参数**

| 参数 | 类型 | 说明 |
|---|---|---|
| `id` | `char` | 当前实现保留的参数，不参与调度判断 |

**返回值**

当前实现正常执行时返回 `1`。

**功能说明**

设置调度请求标志，并通过设置 Timer0 溢出标志请求进入 Timer0 中断处理：

```c
id = id;
OS_SCHED_REASON = 1;
TF0 = 1;

return 1;
```

该接口本身不直接调用调度器，也不直接切换任务。

**调用示例**

```c
os_schedule_request(0);
```

**注意事项**

- `id` 当前没有实际功能，只是保留参数。
- 设置 `TF0` 是请求 Timer0 中断处理的方式，实际执行时机取决于中断使能状态和内核中断处理流程。
- 函数没有自行保存和恢复 `EA`。
- 不应仅根据此函数就断言调用后会立即发生任务切换。

### os_event_set_from_isr

**函数原型**

```c
char os_event_set_from_isr(char obj);
```

**参数**

| 参数 | 类型 | 说明 |
|---|---|---|
| `obj` | `char` | 事件资源槽位编号 |

**返回值**

| 返回值 | 含义 |
|---|---|
| `1` | 事件设置操作完成 |
| `-1` | 资源编号无效 |

**功能说明**

该接口将指定资源的事件值设置为 `1`，将 `pending_signal` 设置为当前 `wait_cnt`，并设置调度请求标志。

核心操作如下：

```c
OS_RES[obj].value = 1;
OS_RES[obj].pending_signal = OS_RES[obj].wait_cnt;
OS_SCHED_REASON = 1;
```

**调用示例**

```c
char result = os_event_set_from_isr(0);
```

**注意事项**

- 资源编号必须小于 `OS_RESOURCE_MAX`。
- 事件值被设置为 `1`，形成保持状态；该函数本身不会清除事件值。
- `pending_signal` 是被赋值为 `wait_cnt`，而不是执行自增操作。
- 该函数没有直接遍历等待任务或调用唤醒函数。
- 具体有多少任务被唤醒，以及等待任务如何处理，应以相关内核调度与资源处理代码为准。
- 函数没有自行关闭或恢复全局中断。

### os_semaphore_post_from_isr

**函数原型**

```c
char os_semaphore_post_from_isr(u8 obj);
```

**参数**

| 参数 | 类型 | 说明 |
|---|---|---|
| `obj` | `u8` | 信号量对应的资源槽位编号 |

**返回值**

| 返回值 | 含义 |
|---|---|
| `1` | 操作完成 |
| `-1` | 资源编号无效 |

**功能说明**

该接口根据资源当前的等待任务数量，采取不同处理方式。

**存在等待任务时**

当 `OS_RES[obj].wait_cnt > 0` 时，函数增加待处理信号计数，并设置调度请求标志：

```c
OS_RES[obj].pending_signal++;
OS_SCHED_REASON = 1;
```

此分支不会直接增加 `value`，也不会直接唤醒任务。

**没有等待任务时**

当 `wait_cnt == 0` 时，如果资源值小于 `255`，则将其加一：

```c
if (OS_RES[obj].value < 255)
{
    OS_RES[obj].value++;
}
```

因此，资源值的最大值为 `255`，达到上限后不会继续增加。

**调用示例**

```c
char result = os_semaphore_post_from_isr(0);
```

**注意事项**

- 资源编号必须小于 `OS_RESOURCE_MAX`。
- 有等待任务时，函数只记录待处理信号并提交调度请求，后续行为由内核处理。
- 没有等待任务时，资源值最多增加至 `255`。
- 函数没有自行关闭或恢复全局中断。
- 该实现的实际语义应结合信号量等待接口及内核对 `pending_signal` 的处理共同理解。

### os_msgq_send_from_isr

**函数原型**

```c
char os_msgq_send_from_isr(os_msgq_t *q, u8 obj, u8 _data);
```

**参数**

| 参数 | 类型 | 说明 |
|---|---|---|
| `q` | `os_msgq_t *` | 消息队列控制块指针 |
| `obj` | `u8` | 与消息队列等待处理相关联的资源槽位编号 |
| `_data` | `u8` | 待发送的单字节数据 |

**返回值**

| 返回值 | 含义 |
|---|---|
| `1` | 数据写入消息队列成功 |
| `-1` | 队列指针为空、资源编号无效或队列已满 |

**功能说明**

该接口在中断环境中向环形消息队列写入一个字节。它依次检查队列指针、资源编号和队列容量；任一检查失败，立即返回 `-1`。

当队列有空闲空间时，函数执行以下操作：

```c
q->buf[q->head] = _data;
q->head = (u8)((q->head + 1) % q->_size);
q->count++;
```

随后，如果对应资源的 `wait_mask` 非零，函数会扫描任务数组，查找第一个 `wait_type == WAIT_MSG_RECV` 的任务。找到后设置调度请求标志、增加该资源的 `pending_signal`，然后结束扫描。

**调用示例**

```c
char result = os_msgq_send_from_isr(&my_queue, 0, 0x55);
```

**注意事项**

- `q` 不能为 `NULL`。
- `obj` 必须小于 `OS_RESOURCE_MAX`。
- 队列已满时，函数立即返回，不执行阻塞等待。
- 该函数会更新环形队列的 `head` 和 `count`，并在匹配条件满足时提交调度请求。
- 当前实现中的任务扫描条件只检查 `OS_TASK[i].wait_type == WAIT_MSG_RECV`，并没有同时检查该任务是否属于 `OS_RES[obj].wait_mask` 对应的等待集合。因此，不能据此保证被扫描到的任务一定在等待当前消息队列。
- 当前代码只记录待处理信号并提交调度请求，不直接调用任务唤醒函数。
- 实现采用无锁操作，并在注释中假设单中断上下文。其并发安全边界取决于实际中断嵌套、任务访问方式及消息队列使用约束。

## 临界区使用建议

临界区用于保护需要避免中断并发访问的关键操作。建议保持进入与退出严格配对，并尽量缩短关闭中断的时间。

```c
os_enter_critical();

/* 访问需要保护的共享状态 */

os_exit_critical();
```

如果使用 `OS_ENTER_CRITICAL()` 和 `OS_EXIT_CRITICAL()` 宏，应确认其定义与当前实现一致。

## 中断与任务通信的使用原则

中断服务程序通常需要快速完成必要处理，再将后续工作交由任务执行。根据本模块提供的实现，可以采用以下原则：

- **单字节资源写入**：使用 `os_queue_send_from_isr()`，但要注意它覆盖资源值，并非 FIFO 队列。
- **事件通知**：使用 `os_event_set_from_isr()` 设置事件状态。
- **信号量释放**：使用 `os_semaphore_post_from_isr()` 记录释放信号或增加资源计数。
- **消息队列发送**：使用 `os_msgq_send_from_isr()` 将数据写入消息队列。
- **调度请求**：需要请求内核重新检查调度条件时，可使用 `os_schedule_request()`。

这些接口并不都采用相同的中断保护方式，也并非全部直接唤醒任务。调用者应根据具体接口的返回值和实现语义处理异常情况。


## 使用说明

- **中断上下文**：`_from_isr` 接口用于在中断服务程序中执行相应的资源操作。调用前应确认接口的适用范围，并遵循系统规定的中断优先级与嵌套规则。
- **调度请求**：`os_schedule_request()` 用于请求内核处理调度，不代表调用后立即发生任务切换。实际切换时机取决于中断处理流程和内核调度机制。
- **资源操作差异**：不同的 ISR 接口分别面向消息队列、事件、信号量等资源，其状态更新和任务唤醒行为可能不同，应按照各自的接口约定使用。
- **任务唤醒与调度**：中断中的资源操作可能使等待任务具备继续运行的条件，但任务何时恢复执行取决于内核的唤醒与调度流程。
- **中断状态查询**：`os_interrupt_id()` 用于获取当前中断标识，`os_in_isr()` 用于查询当前是否处于中断上下文。使用这些接口时，应遵循系统对中断状态和调用上下文的定义。
- **并发与共享资源**：中断服务程序与任务可能共同访问内核资源。设计相关逻辑时，应遵循系统的中断管理和同步约定，不应默认所有 ISR 接口均具备适用于任意嵌套场景的完整并发保护。
