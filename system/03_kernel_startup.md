# HRTOS 内核启动

## 模块介绍

HRTOS 内核启动过程负责将 8051 MCU 从初始运行环境引导至操作系统运行状态，完成内存初始化、内核变量配置、基础任务创建、Timer0 系统时基启动，以及应用初始化入口调用。

当前启动流程主要由用户工程中的 `main()` 和内核中的 `os_idle_task()` 协同完成。

`main()` 负责底层运行环境准备、内核初始参数设置、系统基础任务创建、初始任务栈设置以及 Timer0 启动。

`os_idle_task()` 负责初始化任务等待状态和资源管理状态，调用用户应用初始化入口 `hrtos_main()`，锁定系统配置，并进入永久空闲循环。

系统启动过程中需要特别注意中断状态、任务栈布局和初始化顺序。相关操作与 HRTOS 的 8051 上下文切换机制紧密关联，不应随意调整执行顺序。

## 启动流程

```text
MCU 复位
   │
   ▼
进入 main()
   │
   ▼
清零内部 RAM
   │
   ▼
清理 HRTOS 数据区域
   │
   ▼
初始化内核运行参数
   │
   ▼
创建空闲任务
   │
   ▼
创建系统保留任务
   │
   ▼
设置初始任务栈
   │
   ▼
装载 Timer0 初始计数值
   │
   ▼
配置 Timer0 并开启中断
   │
   ▼
调用 os_idle_task()
   │
   ▼
关闭总中断
   │
   ▼
初始化任务状态与资源状态
   │
   ▼
调用 hrtos_main()
   │
   ▼
锁定系统配置
   │
   ▼
重新开启总中断
   │
   ▼
进入永久 Idle 循环
   │
   ├── 清理已删除的普通任务
   │
   ├── 处理快速任务删除请求
   │
   ├── 执行 Idle Hook
   │
   └── 循环等待后续调度
```

需要注意，以上是源码层面的函数调用和初始化顺序。任务实际何时切换、首次进入哪个用户任务，以及中断返回时如何恢复任务现场，还取决于 HRTOS 的调度和上下文切换实现。

## 系统入口 main()

`main()` 是用户工程中的系统启动入口。该函数在进入 `os_idle_task()` 之前，完成底层内存处理、内核初始变量配置、基础任务创建和 Timer0 启动。

### 内部 RAM 初始化

启动代码首先执行一段嵌入式汇编：

```asm
MOV     R0,#7FH
CLR     A

OS_HRTOS_MAIN_INIT:
MOV     @R0,A
DJNZ    R0,OS_HRTOS_MAIN_INIT
```

执行过程如下：

- 将寄存器 `R0` 设置为 `0x7F`。
- 将累加器 `A` 清零。
- 使用 `@R0` 间接寻址方式向内部 RAM 写入零。
- 每次写入后递减 `R0`，直到循环结束。

该循环将地址 `0x7F` 至 `0x01` 的内部 RAM 单元清零。由于循环在 `R0` 递减到零时退出，地址 `0x00` 不会被这段循环清零。

因此，准确地说，这段代码清零的是内部 RAM 的 `0x01` 至 `0x7F` 地址，而不是完整的 `0x00` 至 `0x7F` 地址范围。

这属于启动阶段的底层内存操作，直接依赖 8051 内部 RAM 地址空间及寄存器使用约定。修改时应同时考虑寄存器组、启动代码和编译器生成代码的影响。

### HRTOS 数据区域初始化

内部 RAM 清理后，启动代码执行：

```c
os_memset(&OS_PROCESS_OK[0], 0, 0x01FF);
```

该调用从 `OS_PROCESS_OK[0]` 的地址开始，按 `os_memset()` 的实际接口语义清零指定长度的数据区域。

这与前面的内部 RAM 汇编清零不同：汇编代码明确操作内部 RAM，而该调用的实际目标地址空间、长度单位及覆盖范围，需要结合 `os_memset()` 的实现和变量存储声明确认。

不能仅凭这行代码就认定清零范围一定从 `OS_CURRENT_TASK` 开始，也不能在没有核实变量布局的情况下将其描述为固定的片外 RAM 地址区间。

启动时必须保证该清零范围有效，并且不会覆盖尚需保留的启动状态或其他内存对象。

## 内核初始参数

完成数据区域清理后，`main()` 设置内核启动阶段需要的变量。

### 初始调度状态

```c
OS_DISPATCH_ID = 1;
OS_CURRENT_TASK = 0;
OS_INTERRUPT_T0 = 0;
OS_INTERRUPT_GAO = 0;
OS_RTOS_YES = 1;
OS_INTERRUPT_PROTECT = 0;
OS_TIME_ONCE = OS_TIME_ONCE_DEFAULT;
```

这些变量分别参与系统初始调度状态、当前任务标识、中断相关状态、运行模式以及时间片参数管理。

其中：

- `OS_CURRENT_TASK = 0`：将初始任务标识设置为零。
- `OS_RTOS_YES = 1`：将系统运行模式变量设置为启用状态。
- `OS_TIME_ONCE = OS_TIME_ONCE_DEFAULT`：使用配置文件提供的默认时间片计数参数。
- `OS_INTERRUPT_T0`、`OS_INTERRUPT_GAO` 和 `OS_INTERRUPT_PROTECT`：初始化相关中断状态及保护状态。

这些变量的精确语义应以各自的内核使用位置和状态转换逻辑为准，不能仅凭变量名推断完整行为。

### 快速任务删除状态

```c
OS_KUAI_PROCESS_A_DEL = 0;
OS_KUAI_PROCESS_B_DEL = 0;
```

这两个变量用于记录快速任务 A、快速任务 B 的删除请求状态。

启动时将其清零，避免在初始化阶段遗留无效的删除请求。运行过程中，`os_idle_task()` 会检查这两个标志，并分别调用 `os_task_cleanup()` 处理对应快速任务的清理工作。

### 系统 Tick 计数器

```c
OS_TICK_COUNT_L = 0;
OS_TICK_COUNT_H = 0;
```

两个变量分别保存累计 Tick 计数的低 16 位和高 16 位。

组合关系如下：

```text
32 位系统 Tick 计数
┌──────────────────┬──────────────────┐
│   高 16 位       │    低 16 位      │
│ OS_TICK_COUNT_H  │ OS_TICK_COUNT_L  │
└──────────────────┴──────────────────┘
```

在计数逻辑正确处理低 16 位溢出的前提下，高低两个计数器可以扩展系统累计 Tick 的表示范围。其实际更新时间及溢出处理方式应以 Timer0 中断实现为准。

### 临界区嵌套计数

```c
os_critical_nesting = 0;
```

将临界区嵌套状态初始化为零，使内核从预期的初始状态开始管理临界区。

该变量的作用与临界区实现方式相关，启动时应保证其初值与中断开关状态和内核临界区机制相匹配。

## 系统基础任务创建

### 创建空闲任务

```c
os_task_create(os_idle_task, 0, 0, 2);
```

该调用将 `os_idle_task()` 注册为系统空闲任务。

从当前启动代码可见，创建参数依次为任务入口、第二个参数 `0`、优先级参数 `0` 和最后一个参数 `2`。各参数的完整含义应以 `os_task_create()` 的函数声明和实现为准。

空闲任务承担系统初始化后续阶段及永久空闲循环中的工作，包括：

- 调用用户初始化入口 `hrtos_main()`。
- 锁定系统配置。
- 检查普通任务的删除状态。
- 处理快速任务删除请求。
- 执行已注册的 Idle Hook。

空闲任务的创建并不意味着它立即开始执行。实际执行时机取决于启动代码、当前任务状态以及上下文切换机制。

### 创建系统保留任务

```c
os_task_create(
    (unsigned int)os_interrupt_exit, 0, 9, 0);

os_task_create(
    (unsigned int)os_interrupt_exit, 0, 10, 0);
```

启动代码还创建了两个入口指向 `os_interrupt_exit` 的系统保留任务，参数中的优先级值分别为 `9` 和 `10`。

这些任务与 HRTOS 的中断处理和退出机制有关。由于入口直接使用 `os_interrupt_exit`，其实际执行语义取决于内核如何组织任务入口、异常路径及中断上下文。

这部分属于内核内部约定，不应将其简单理解为两个普通的用户应用任务，也不应在未核实调度和中断实现前推断其完整运行路径。

## 初始任务栈设置

```c
SP = OS_JINCHENG_JILU_SP[0] - 2;
```

该语句根据任务记录中的栈位置设置 8051 的栈指针 `SP`。

结合代码注释，该调整用于匹配初始任务进入时预期的栈布局，使首次进入初始任务时的栈状态符合 HRTOS 的上下文切换约定。

8051 的上下文切换通常与返回地址、寄存器现场及栈指针状态紧密相关。`SP` 的初始值不能脱离任务创建代码、栈初始化代码和汇编切换实现单独修改。

移植到不同编译器或不同 8051 内核实现时，应重新核对：

- 任务栈的初始布局。
- 返回地址的压入与弹出方式。
- 寄存器现场保存和恢复顺序。
- 首次进入任务时的栈指针位置。

## Timer0 系统时基初始化

HRTOS 当前启动代码使用 Timer0 作为系统时间基准。

### 计算初始计数值

```c
OS_T0_TH0 = (65535 - OS_TIME_T0) / 256;
OS_T0_TL0 = (65535 - OS_TIME_T0) % 256;
```

该代码将计算结果拆分为高、低字节，分别保存至 `OS_T0_TH0` 和 `OS_T0_TL0`。

随后：

```c
TH0 = OS_T0_TH0;
TL0 = OS_T0_TL0;
```

将计算结果写入 Timer0 的高、低字节寄存器。

对于 16 位定时器，常见的重装值计算形式为：

\[
R = 65536-N
\]

其中 \(N\) 是期望的定时器计数次数，\(R\) 是初始计数值。实际溢出周期还取决于目标芯片的定时器计数时钟、分频设置和工作模式。

当前代码使用 `65535 - OS_TIME_T0`，与常见的 `65536 - N` 形式相差一个计数单位。是否属于有意设计，应结合 HRTOS 的时间基准定义及目标芯片的实测周期确认。

### 配置并启动 Timer0

```c
TMOD |= 0x01;

ET0 = 1;
TR0 = 1;
EA = 1;
```

各操作的作用如下：

- `TMOD |= 0x01`：设置 Timer0 的模式选择位，使其进入模式 1，即 16 位定时器模式。该操作不会清除 `TMOD` 的其他位。
- `ET0 = 1`：允许 Timer0 中断。
- `TR0 = 1`：启动 Timer0。
- `EA = 1`：开启 CPU 总中断允许。

Timer0 在系统运行后用于驱动系统 Tick、时间片管理及相关调度逻辑。其完整中断处理过程由 Timer0 的中断服务程序实现。

由于 Timer0 被系统用作时基，应用程序不应在没有确认内核约定的情况下擅自修改其工作模式、计数寄存器或中断配置。

## 进入 os_idle_task()

完成初始变量、任务和 Timer0 配置后，`main()` 直接调用：

```c
os_idle_task();
```

这不是一次普通的任务创建操作，而是启动代码直接调用空闲任务函数，继续完成系统运行阶段的初始化。

在该函数执行过程中，系统先关闭总中断，完成运行状态初始化和用户应用初始化，然后重新开启总中断并进入永久循环。

如果 `os_idle_task()` 意外返回，`main()` 后续代码将继续执行。因此，正常运行情况下，空闲任务应保持永久循环，不应返回到启动函数的后续路径。

## 空闲任务初始化

### 关闭总中断

`os_idle_task()` 开始时执行：

```c
EA = 0;
```

在初始化任务状态、资源状态以及调用 `hrtos_main()` 期间，函数保持总中断关闭，避免相关初始化过程被中断打断。

这也意味着 `hrtos_main()` 在当前实现下执行时，总中断处于关闭状态。应用初始化函数应避免依赖需要中断持续运行才能完成的同步操作，否则可能造成等待无法结束。

### 初始化 Hook 与调度状态

```c
g_idle_hook = 0;
g_slab_overflow_hook = 0;

OS_SCHED_REASON = 0;
OS_CFG_LOCK = 0;
```

其中：

- `g_idle_hook`：清空 Idle Hook 函数指针。
- `g_slab_overflow_hook`：清空 Slab 溢出处理 Hook 函数指针。
- `OS_SCHED_REASON`：清除调度原因状态。
- `OS_CFG_LOCK = 0`：初始化阶段允许注册相关配置项。

这一步使系统从明确的初始状态开始运行，并允许用户在 `hrtos_main()` 中完成应用配置。

### 初始化普通任务状态

```c
for (i = 0; i < OS_PROCESS_MAX; i++)
{
    OS_TASK[i].wait_type = WAIT_NONE;
    OS_TASK[i].state = READY;
    OS_TASK[i].wait_tick = 0;
    OS_TASK[i].wait_obj = OS_INVALID_ID;
}
```

循环初始化普通任务数组中的等待状态及相关字段：

- `wait_type` 设置为 `WAIT_NONE`。
- `state` 设置为 `READY`。
- `wait_tick` 清零。
- `wait_obj` 设置为 `OS_INVALID_ID`。

这些赋值用于建立统一的任务状态初值。它们并不意味着所有普通任务都会立即执行；任务是否有效、入口是否注册以及何时获得运行机会，仍取决于任务创建和调度逻辑。

该循环的范围为 `0` 至 `OS_PROCESS_MAX - 1`，不应直接据此推断快速任务的状态也在此处完成初始化。

### 初始化快速任务等待状态

```c
OS_WAIT_DI2[0] = 0;
OS_WAIT_DI2[1] = 0;
```

该操作将两个相关状态项清零。其具体语义应结合快速任务等待与唤醒机制理解，不宜仅凭变量名称推断其完整含义。

### 初始化资源状态

```c
for (i = 0; i < OS_RESOURCE_MAX; i++)
{
    OS_RES[i].value = 0;
    OS_RES[i].owner = OS_INVALID_ID;
    OS_RES[i].wait_cnt = 0;
    OS_RES[i].wait_mask = 0;
    OS_RES[i].pending_signal = 0;
}
```

循环初始化资源管理数组中的状态：

- `value` 清零。
- `owner` 设置为 `OS_INVALID_ID`。
- `wait_cnt` 清零。
- `wait_mask` 清零。
- `pending_signal` 清零。

这些操作为资源管理建立初始状态，避免资源所有者、等待信息或待处理信号保留未初始化值。

资源管理的具体行为仍由对应 IPC 或资源 API 决定。启动阶段的清零只负责建立初始状态，不代表所有资源已经由应用程序完成配置。

## 用户应用初始化 hrtos_main()

完成空闲任务内部的初始状态设置后，系统调用：

```c
hrtos_main();
```

`hrtos_main()` 是用户应用的初始化入口，用于完成系统启动阶段所需的应用配置。

典型用途包括：

- 创建用户任务。
- 初始化应用使用的 IPC 对象。
- 配置驱动和应用模块。
- 注册允许在启动阶段设置的 Hook 或其他配置项。

示例：

```c
void hrtos_main(void)
{
    /* 创建应用任务 */
    os_task_create(task1, ...);
    os_task_create(task2, ...);

    /* 初始化应用所需资源 */
    os_sem_init(...);
}
```

以上仅为接口使用示意，实际参数应以 HRTOS 对应 API 的定义为准。

### 初始化阶段的约束

`hrtos_main()` 执行时，`os_idle_task()` 已经关闭总中断。因此：

- 不应等待依赖 Timer0 中断才能结束的延时或同步条件。
- 不应在初始化入口中执行永久循环。
- 应避免依赖串口中断、外部中断等必须由 ISR 驱动的流程来完成阻塞式等待。
- 应在该阶段完成必要的任务创建和配置，再返回内核。

如果需要执行依赖中断的初始化流程，应重新设计初始化顺序，或在符合内核约定的阶段完成，而不能默认初始化期间中断始终开启。

## 锁定配置并开启中断

`hrtos_main()` 返回后，空闲任务执行：

```c
OS_CFG_LOCK = 1;
EA = 1;
```

`OS_CFG_LOCK = 1` 表示启动阶段的配置窗口结束，后续是否允许注册配置项由相关接口的锁检查逻辑决定。

随后 `EA = 1` 重新开启总中断，系统进入中断驱动的正常运行阶段。

需要注意，`EA = 1` 是直接开启总中断，并不是恢复进入函数前的中断状态。该行为是当前启动流程的一部分，修改时应结合整个系统的中断管理约定进行评估。

## 永久空闲循环

完成初始化并重新开启总中断后，`os_idle_task()` 进入永久循环：

```c
while (1)
{
    EA = 0;

    for (i = 1; i < OS_PROCESS_MAX; i++)
    {
        if (OS_TASK[i].state == DEAD)
        {
            os_task_cleanup(i);
        }
    }

    if (OS_KUAI_PROCESS_A_DEL)
    {
        os_task_cleanup(OS_PROCESS_MAX);
        OS_KUAI_PROCESS_A_DEL = 0;
    }

    if (OS_KUAI_PROCESS_B_DEL)
    {
        os_task_cleanup(OS_PROCESS_MAX + 1);
        OS_KUAI_PROCESS_B_DEL = 0;
    }

    EA = 1;

    if (g_idle_hook)
    {
        g_idle_hook();
    }
}
```

### 普通任务清理

循环从任务索引 `1` 开始，遍历到 `OS_PROCESS_MAX - 1`，检查任务状态是否为 `DEAD`。

如果任务已经进入删除状态，则调用：

```c
os_task_cleanup(i);
```

进行相应的资源清理。

该循环刻意没有遍历普通任务索引 `0`。结合启动代码中任务 `0` 被用作系统空闲任务，可以看出空闲任务本身不在此处的普通任务删除扫描范围内。

### 快速任务清理

空闲循环还检查两个快速任务删除标志：

```c
OS_KUAI_PROCESS_A_DEL
OS_KUAI_PROCESS_B_DEL
```

当相应标志置位时，分别调用：

```c
os_task_cleanup(OS_PROCESS_MAX);
os_task_cleanup(OS_PROCESS_MAX + 1);
```

随后清除对应标志。

由此可见，快速任务删除请求通过标志交由空闲循环处理。快速任务自身的删除请求设置条件和安全时机，需要结合快速任务管理代码进一步确认。

### Idle Hook

任务清理完成后，空闲循环重新开启总中断，并在 `g_idle_hook` 非空时调用该函数指针：

```c
if (g_idle_hook)
{
    g_idle_hook();
}
```

Idle Hook 为用户提供空闲阶段的扩展入口，可用于适合该执行环境的轻量级处理。

Hook 运行在空闲任务的执行上下文中。用户应避免在其中执行长时间阻塞、永久循环或不可控的耗时操作，否则会影响空闲任务后续处理工作的及时性。

## 启动阶段的中断状态

当前源码的关键中断状态变化如下：

```text
main() 初始化阶段
       │
       ▼
配置内核变量与任务
       │
       ▼
ET0 = 1
TR0 = 1
EA = 1
       │
       ▼
调用 os_idle_task()
       │
       ▼
EA = 0
       │
       ▼
初始化任务、资源与 Hook
       │
       ▼
调用 hrtos_main()
       │
       ▼
OS_CFG_LOCK = 1
EA = 1
       │
       ▼
进入永久空闲循环
```

这里有一个重要的实现特点：`main()` 在调用 `os_idle_task()` 之前已经执行 `EA = 1`，而 `os_idle_task()` 入口随后再次执行 `EA = 0`。因此，不能将整个启动过程描述为从头到尾始终关闭中断。

同时，Timer0 在 `main()` 中已经启动，之后才进入 `os_idle_task()`。如果 Timer0 中断恰好在这两个阶段之间发生，具体行为取决于 Timer0 ISR 对相关状态的处理方式。需要结合 ISR 源码验证该阶段是否存在依赖特定初始化顺序的边界条件。

## 启动约束与注意事项

### 内存初始化范围

内部 RAM 汇编清零与 `os_memset()` 清零属于不同的操作，必须分别确认其地址空间和覆盖范围。

尤其需要核对 `os_memset(&OS_PROCESS_OK[0], 0, 0x01FF)` 的目标区域是否与其他变量、栈区或特殊存储区重叠。

### 任务栈布局

`SP = OS_JINCHENG_JILU_SP[0] - 2` 与 HRTOS 的任务初始栈布局相关。修改任务创建函数、汇编切换代码或编译器设置时，必须重新验证首次进入任务和任务切换过程。

### Timer0 独占约定

当前系统使用 Timer0 作为系统时基，并开启 Timer0 中断。应用程序不应在未经评估的情况下将 Timer0 同时用于其他定时功能，否则可能破坏系统 Tick、时间片管理和调度时序。

### 初始化期间的中断限制

`hrtos_main()` 在 `EA = 0` 的状态下执行。任何依赖中断持续运行才能完成的操作，都需要重新评估是否适合在该阶段执行。

### 配置锁定

`OS_CFG_LOCK` 在调用 `hrtos_main()` 前被设置为 `0`，返回后设置为 `1`。应用配置接口是否受该标志约束，应以对应 API 的实现为准。

### 空闲任务不能正常返回

`os_idle_task()` 的正常执行路径是永久循环。如果该函数意外返回，`main()` 将继续执行其后续代码，而不是重新启动操作系统。因此，空闲任务必须保持其设计的长期运行行为。

## 启动问题排查

### 系统无法进入正常运行状态

检查内部 RAM 初始化、数据区域清理、基础任务创建、初始栈指针、Timer0 配置以及中断入口是否正确。

### 用户任务未执行

检查 `hrtos_main()` 是否正常返回、任务创建接口是否成功、任务状态与优先级是否符合预期，以及 Timer0 中断和调度路径是否正常。

### 初始化阶段卡住

优先检查 `hrtos_main()` 是否调用了依赖中断的延时、同步或驱动接口。当前实现会在调用该函数前关闭总中断，因此相关等待可能无法完成。

### 任务删除后未完成清理

检查普通任务是否进入 `DEAD` 状态，以及快速任务删除标志是否正确置位、清除；同时确认空闲循环是否持续获得执行机会。

### 系统运行时序异常

检查 Timer0 的计数时钟、重载值、工作模式、ISR 执行路径及任务切换实现。仅确认 `TR0` 和 `ET0` 已设置，并不能证明系统 Tick 周期一定准确。

## 总结

HRTOS 的启动流程由 `main()` 与 `os_idle_task()` 协同完成。

`main()` 负责底层内存处理、内核初始变量设置、基础任务创建、初始栈设置以及 Timer0 启动。`os_idle_task()` 负责初始化任务和资源状态、执行用户初始化入口、锁定配置，并进入永久空闲循环，持续处理任务清理请求与 Idle Hook。

整个过程依赖明确的初始化顺序、中断状态约定和 8051 上下文切换机制。维护或移植启动代码时，应以实际内核实现为依据，重点验证内存覆盖范围、初始栈布局、Timer0 时基和初始化期间的中断行为。
