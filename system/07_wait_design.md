# HRTOS 任务等待与唤醒模块

## 模块概述

任务等待与唤醒模块是 HRTOS 内核任务状态管理与调度控制的基础模块，负责统一处理任务阻塞、等待关系登记、唤醒结果记录、等待上下文清理及任务就绪状态恢复。

在实时操作系统中，任务并不总是持续执行。当任务需要等待指定时间，或者等待信号量、互斥锁、邮箱、消息队列及事件等条件满足时，内核需要暂时取消该任务的正常调度资格，并在相应条件满足或等待超时后恢复任务运行。

HRTOS 通过 `os_wait()` 和 `wake_task()` 将等待处理与唤醒处理分离：

- `os_wait()`：记录任务等待信息，将任务设置为等待状态，并请求内核进行任务调度。
- `wake_task()`：清理任务等待记录，设置唤醒结果，将任务恢复为就绪状态，并请求内核重新调度。
- `os_res_init()`：初始化资源控制块，为资源等待关系管理提供基础状态。

该模块不直接负责信号量计数、互斥锁所有权或邮箱数据收发等具体业务逻辑，而是为这些上层功能提供统一的任务等待与唤醒机制。

## 模块组成

| 源文件 | 核心职责 |
|---|---|
| `wait.c` | 统一处理任务等待请求、等待上下文记录、资源等待登记及任务阻塞 |
| `wake_task.c` | 清理任务等待状态、记录唤醒结果、恢复任务就绪状态 |
| `res_init.c` | 初始化资源控制块及其等待记录 |

## 核心数据与状态

### 任务等待上下文

`os_wait()` 使用任务控制块中的等待字段记录当前任务的等待信息。

| 字段 | 作用 |
|---|---|
| `wait_type` | 标记任务当前的等待类型 |
| `wait_obj` | 记录关联的等待对象编号 |
| `wait_tick` | 记录等待时间参数，以系统 Tick 为单位 |
| `wait_flag` | 记录任务的等待或唤醒结果 |
| `state` | 标记任务当前的运行状态 |

任务进入等待状态时，内核写入相应的等待信息，并将 `state` 设置为 `WAIT`。任务被唤醒时，内核清除等待上下文，将状态恢复为 `READY`。

其中，`wait_flag` 用于向任务提供等待结果。根据 `os_wait()` 中的注释，主要结果包括：

- `WAIT_TIMEOUT`：等待超时。
- `WAIT_SIGNAL`：因资源或其他唤醒操作而恢复运行。
- `0`：等待参数无效，或当前任务已经处于等待状态等异常情况。

具体 API 的最终返回值还取决于各上层接口自身的处理逻辑。

### 资源控制块

`os_res_init()` 对 `OS_RESOURCE` 控制块执行以下初始化：

| 字段 | 初始化值 | 说明 |
|---|---|---|
| `value` | `0` | 资源初始值 |
| `owner` | `OS_INVALID_ID` | 初始时无有效拥有者 |
| `wait_cnt` | `0` | 等待任务计数清零 |
| `wait_mask` | `0` | 清除所有资源等待位 |

`OS_RESOURCE` 还包含 `pending_signal` 字段，但当前提供的 `os_res_init()` 并未对其赋值。因此，不能仅凭该函数认定资源控制块的所有字段都会被完整初始化；需要结合资源创建和其他初始化代码确认该字段的初始状态。

### 资源等待位图

HRTOS 使用 `wait_mask` 记录等待资源的标准任务。每一位对应一个任务编号，置位表示该任务已登记为该资源的等待者。

```c
OS_RES[obj].wait_mask |= ((u16)1 << tid);
```

任务进入资源等待路径时，`os_wait()` 设置对应位，并递增 `wait_cnt`。

任务被唤醒时，`wake_task()` 根据任务记录的 `wait_obj` 清除对应等待位，并在 `wait_cnt` 非零时递减计数。

这种位图机制能够以紧凑的数据结构维护任务与资源之间的等待关系，避免为每个等待任务单独建立链表节点。

需要注意，当前 `wait_mask` 为 16 位，而 `os_wait()` 中资源等待登记使用当前任务编号 `tid` 进行移位。该资源等待路径主要面向标准任务；高速任务使用独立的延时等待处理路径。

## 任务等待机制

### 等待处理流程

`os_wait(type, obj, tick)` 是统一等待入口。函数首先进入临界区并读取当前任务编号，然后根据等待类型执行相应处理。

    B --> C["获取当前任务 ID"]
    C --> D{"type == WAIT_DELAY?"}
    D -- 是 --> E{"tick == 0?"}
    E -- 是 --> F["开启总中断并返回 WAIT_TIMEOUT"]
    E -- 否 --> G{"是否为高速任务?"}
    G -- 是 --> H["记录高速任务延时计数"]
    H --> I["设置调度触发标志"]
    I --> J["开启总中断并触发 T0"]
    J --> K["返回 WAIT_TIMEOUT"]
    G -- 否 --> L["记录等待上下文"]
    L --> M["设置任务状态为 WAIT"]
    M --> N["清除任务调度资格"]
    N --> O["设置调度触发标志"]
    O --> P["开启总中断并触发 T0"]
    P --> Q["返回 wait_flag"]
    D -- 否 --> R{"当前任务是否已在等待?"}
    R -- 是 --> S["开启总中断并返回 0"]
    R -- 否 --> T{"obj 是否超出资源范围?"}
    T -- 是 --> U["开启总中断并返回 0"]
    T -- 否 --> V["记录等待上下文"]
    V --> W["登记资源等待位图及计数"]
    W --> X["设置任务状态为 WAIT"]
    X --> Y["清除任务调度资格"]
    Y --> Z["设置调度触发标志"]
    Z --> AA["开启总中断并触发 T0"]
    AA --> AB["返回 wait_flag"]</CodeBlock>

### 普通任务的阻塞过程

对于标准任务，等待处理主要包含以下步骤：

1. **检查当前等待状态。** 如果 `OS_TASK[tid].wait_type != WAIT_NONE`，函数认为当前任务已经处于等待状态，开启总中断后返回 `0`，不重复登记等待。
2. **检查等待对象。** 对于非 `WAIT_DELAY` 类型的等待，检查 `obj` 是否小于 `OS_RESOURCE_MAX`。超出资源范围时返回 `0`。
3. **记录等待上下文。** 写入 `wait_type`、`wait_obj`、`wait_tick`，并将 `wait_flag` 清零。
4. **登记资源等待关系。** 对于非延时等待且 `obj != OS_INVALID_ID` 的情况，将当前任务对应的位写入资源 `wait_mask`，并递增 `wait_cnt`。
5. **设置任务阻塞状态。** 将任务状态设为 `WAIT`，同时清除 `OS_PROCESS_OK[tid]` 的 bit0，取消该任务的正常调度资格。
6. **请求调度。** 设置 `OS_SCHED_REASON = 1`，开启总中断并设置 `TF0 = 1`，请求通过 Timer0 中断路径进行调度处理。

任务进入等待状态后，`os_wait()` 最后返回 `OS_TASK[tid].wait_flag`。该函数本身并不包含等待循环，而是通过任务状态变化和调度机制使当前任务暂时退出执行；任务恢复运行后，再从原调用位置继续执行并取得返回值。

### 延时等待的特殊处理

当 `type == WAIT_DELAY` 时，`os_wait()` 走独立的延时处理分支。

对于 `tick == 0` 的请求，函数直接开启总中断并返回 `WAIT_TIMEOUT`，不执行阻塞操作。

对于标准任务，函数记录等待上下文，将任务状态设为 `WAIT`，清除其正常调度资格，并请求调度。

对于高速任务，函数不使用标准任务的统一等待上下文，而是根据任务编号分别处理：

- `tid == OS_PROCESS_MAX`：清零 `OS_KUAI_PROCESS_A`，将 `tick` 写入 `OS_WAIT_DI2[0]`。
- `tid == OS_PROCESS_MAX + 1`：清零 `OS_KUAI_PROCESS_B`，将 `tick` 写入 `OS_WAIT_DI2[1]`。

随后设置调度触发标志、开启总中断并触发 Timer0 中断。该路径不会像标准任务的延时路径一样填写 `OS_TASK[tid]` 的等待字段，也不会将高速任务加入标准资源等待位图。

需要注意：高速任务分支中，`EA = 1` 和 `TF0 = 1` 之后立即返回 `WAIT_TIMEOUT`，因此这个返回值不能简单解释为实际延时时间已经结束。高速任务的延时行为需要结合 `OS_WAIT_DI2` 的更新逻辑及调度实现理解。

## 任务唤醒机制

### 唤醒处理流程

`wake_task(tid, flag)` 用于唤醒指定任务。调用时，函数根据任务记录的等待对象清理资源等待关系，检查任务是否已删除或处于删除准备状态，然后写入唤醒结果并恢复任务就绪状态。

<CodeBlock language="mermaid">flowchart TD
    A["调用 wake_task(tid, flag)"] --> B["关闭总中断 EA = 0"]
    B --> C["读取任务 wait_obj"]
    C --> D{"wait_obj != OS_INVALID_ID?"}
    D -- 是 --> E["清除资源 wait_mask 对应位"]
    E --> F{"wait_cnt 是否非零?"}
    F -- 是 --> G["wait_cnt 递减"]
    F -- 否 --> H["继续处理"]
    G --> H
    D -- 否 --> H
    H --> I{"任务已删除或处于 DEAD 状态?"}
    I -- 是 --> J["开启总中断并返回"]
    I -- 否 --> K["写入 wait_flag = flag"]
    K --> L["清除等待上下文"]
    L --> M["state = READY"]
    M --> N["恢复 OS_PROCESS_OK bit0"]
    N --> O["设置 OS_SCHED_REASON = 1"]
    O --> P["开启总中断"]
    P --> Q["设置 TF0 = 1"]
    Q --> R["结束"]
</CodeBlock>

### 唤醒处理的关键步骤

**清理资源等待记录**

函数首先读取任务的 `wait_obj`。如果该字段不是 `OS_INVALID_ID`，则清除该任务在对应资源 `wait_mask` 中的位，并在 `wait_cnt` 非零时递减计数。

这一步用于解除任务与原等待资源之间的登记关系。资源等待记录的清理发生在任务删除状态检查之前。

**检查任务状态**

如果 `OS_PROCESS_OK[tid] == 0`，函数将其视为已删除任务；如果任务状态为 `DEAD`，则视为处于删除准备状态。两种情况下均开启总中断并直接返回，不再执行正常唤醒流程。

**记录唤醒结果并清理上下文**

对于可以正常唤醒的任务，函数将 `flag` 写入 `wait_flag`，然后将以下字段恢复为无等待状态：

- `wait_type = WAIT_NONE`
- `wait_obj = OS_INVALID_ID`
- `wait_tick = 0`

`wait_flag` 不会在该步骤中清零，因此可以保留此次唤醒的结果，供任务恢复执行后读取。

**恢复任务就绪状态**

函数将任务状态设置为 `READY`，并执行：

```c
OS_PROCESS_OK[tid] |= 1;
```

该操作恢复 `OS_PROCESS_OK` 的 bit0，即重新赋予任务正常调度资格。随后设置 `OS_SCHED_REASON = 1`，开启总中断并通过 `TF0 = 1` 请求调度处理。

需要注意，恢复任务就绪状态不等于立即执行该任务。实际运行哪个任务仍由 HRTOS 的调度机制决定。

## 资源初始化机制

`os_res_init(OS_RESOURCE *r)` 负责初始化资源控制块的主要状态：

```c
r->value = 0;
r->owner = OS_INVALID_ID;
r->wait_cnt = 0;
r->wait_mask = 0;
```

该函数不接收资源编号，而是接收资源控制块指针，由调用方确定要初始化的资源。

初始化后，资源值归零、拥有者失效，等待计数和等待位图均清空。该函数本身没有关闭或恢复总中断，也没有初始化 `pending_signal` 字段。因此，调用时机及完整初始化要求应由资源创建流程保证。

## 等待与唤醒的协作关系

任务等待和唤醒不是两个独立的操作，而是通过任务控制块和资源等待位图形成完整的状态管理过程。

<CodeBlock language="mermaid">sequenceDiagram
    participant T as 等待任务
    participant W as os_wait()
    participant R as OS_RESOURCE
    participant S as 调度机制
    participant K as wake_task()

    T->>W: 请求等待资源
    W->>W: 检查等待状态及对象
    W->>R: 登记 wait_mask / wait_cnt
    W->>W: 设置 WAIT，取消调度资格
    W->>S: 设置调度触发标志并触发 T0
    Note over T,S: 等待任务暂时退出正常执行
    K->>R: 清除对应等待位并更新 wait_cnt
    K->>K: 写入唤醒结果
    K->>K: 清除等待上下文
    K->>K: 恢复 READY 和调度资格
    K->>S: 请求重新调度
    S-->>T: 任务获得调度后恢复执行
    T->>T: 从等待调用处继续执行</CodeBlock>

该协作关系体现了模块的两个核心目标：

- **状态一致性：** 通过等待上下文和资源等待位图记录任务当前的等待关系，并在唤醒时清理对应记录。
- **调度协作：** 通过任务状态、`OS_PROCESS_OK`、`OS_SCHED_REASON` 和 Timer0 触发机制，将阻塞与唤醒操作交给内核调度流程处理。

## 设计特点

### 统一等待入口

不同内核功能可以通过 `os_wait()` 进入统一等待机制，减少各模块重复实现任务阻塞状态管理的需要。等待类型用于区分延时等待和资源等待，等待对象用于关联相应资源。

### 位图式等待关系管理

资源控制块使用 `wait_mask` 记录等待任务，使用 `wait_cnt` 维护等待数量。标准任务进入资源等待路径时登记对应位，唤醒时清除对应位。

### 等待结果显式传递

内核使用 `wait_flag` 保存唤醒结果，使任务在恢复运行后能够获取等待结束的原因。上层 API 可以根据自身语义进一步处理这一结果。

### 与调度机制解耦

`os_wait()` 和 `wake_task()` 负责更新任务状态并请求调度，而不是在函数内部直接选择并运行下一个任务。任务切换由内核调度机制完成。

### 高速任务独立处理延时

高速任务的延时请求通过专用状态变量和计数数组处理，不直接进入标准任务的资源等待登记流程。这种分支体现了高速任务与标准任务在等待管理上的实现差异。

## 使用注意事项

- **等待对象必须有效。** 非延时等待的 `obj` 需要处于有效资源编号范围内；`os_wait()` 对超范围对象返回 `0`。
- **重复等待会被拒绝。** 当前任务的 `wait_type` 不为 `WAIT_NONE` 时，`os_wait()` 不会重复登记等待。
- **唤醒结果需要正确解释。** `WAIT_SIGNAL` 和 `WAIT_TIMEOUT` 表示不同的唤醒原因，但上层 API 的最终返回值可能经过额外处理。
- **唤醒不等于资源获取成功。** 任务被唤醒只说明等待状态结束；是否成功取得资源，应由具体资源 API 的实现决定。
- **资源等待位图与计数必须保持一致。** `wake_task()` 按任务记录的 `wait_obj` 清除等待位，并在计数非零时递减；调用方需要保证任务等待上下文与资源记录相匹配。
- **删除状态会影响唤醒处理。** 已删除或处于 `DEAD` 状态的任务不会执行正常的唤醒状态恢复流程。
- **资源初始化需要完整性保证。** `os_res_init()` 未初始化 `pending_signal`，完整初始化应由资源创建流程结合实际使用情况保证。
- **总中断状态需要结合接口约定理解。** 当前实现使用 `EA = 0` 进入临界区、使用 `EA = 1` 重新开启总中断，并非保存和恢复调用前的 EA 状态。调用环境应遵循该内核的中断管理约定。

## 小结

HRTOS 任务等待与唤醒模块通过 `os_wait()`、`wake_task()` 和 `os_res_init()`，建立了从等待登记、任务阻塞、唤醒结果记录到任务重新就绪的基础流程。它将任务状态管理与具体资源操作分离，为信号量、互斥锁、邮箱、消息队列及其他等待机制提供公共内核支持，并通过调度触发机制与 HRTOS 的任务调度流程协同工作。
