# HRTOS 设计原则

## 模块介绍

HRTOS 面向 8051 系列微控制器设计，以轻量化内核为基础，围绕任务调度、中断管理、资源同步、栈空间管理和应用接口构建完整的实时操作系统运行环境。

与直接将通用操作系统架构移植到 8 位微控制器上的设计思路不同，HRTOS 充分考虑 8051 的寄存器组、内部 RAM、外部 RAM、指令执行特征及中断机制，将内核调度、上下文保存和内存布局作为整体进行设计。

HRTOS 的设计不仅关注内核本身的代码规模和运行开销，也重视系统接口的一致性、模块之间的协作关系，以及开发者在实际工程中的使用体验。随着版本迭代，内核机制、驱动接口、通信功能、Shell、示例程序和技术文档持续完善，逐步形成面向 8051 应用开发的完整软件体系。

本文档介绍 HRTOS 的核心设计原则，以及这些原则在内核架构、内存管理、接口设计和性能优化中的体现。

## 主要职责

设计原则主要用于指导以下方面：

- **内核架构**：明确任务管理、调度、中断和资源管理之间的职责边界。
- **内存管理**：根据 8051 的存储空间特点规划变量、任务栈和上下文区域。
- **实时调度**：通过优先级机制、调度请求和任务状态管理组织任务执行。
- **中断处理**：控制中断路径上的内核操作，协调中断处理与任务调度。
- **API 设计**：提供结构清晰、行为一致的内核接口。
- **性能优化**：围绕上下文切换、任务唤醒和关键执行路径持续改进。
- **工程集成**：通过驱动、通信模块、Shell 和示例降低系统接入成本。
- **持续维护**：在保持架构稳定的前提下，逐步完善功能、修复缺陷并补充验证资料。

## 核心设计原则

### 1. 轻量化内核与完整功能并重

**设计原则**

在有限的存储资源下，以紧凑的内核实现覆盖实际应用所需的任务调度、延时等待、资源同步和任务间通信等基础能力，并通过外围模块扩展系统功能。

**设计体现**

- 使用紧凑的数据结构管理任务及其运行状态。
- 采用固定规模的任务、资源和消息队列管理结构。
- 将内核机制与驱动、通信协议、Shell 等功能模块分离。
- 避免为通用性引入不必要的抽象层。
- 根据 8051 的资源条件控制功能实现的内存成本。

**设计目标**

使系统既能适应资源有限的 8051 芯片，又能为实际工程提供超出单纯任务切换的完整软件支持。内核保持精简，应用能力则通过模块化扩展逐步增强。

### 2. 面向 8051 架构进行原生优化

**设计原则**

以内核运行于 8051 系列处理器为前提，将处理器寄存器、存储空间和中断机制直接纳入架构设计，而不是将其他处理器上的实现方式简单照搬过来。

**设计体现**

- 根据 DATA、IDATA 和 XDATA 的特性安排内核变量与管理数组。
- 利用 8051 寄存器组机制支持不同任务执行路径。
- 针对普通任务与高速任务设计不同的上下文保存策略。
- 结合定时器中断和调度请求机制组织任务切换。
- 根据具体芯片的 RAM 容量、定时器资源和编译工具链调整移植配置。

**设计目标**

让内核的数据布局、任务切换和中断处理方式与目标处理器相匹配，在有限硬件资源内取得性能、内存占用和功能完整性之间的平衡。

### 3. 分层任务机制与差异化上下文管理

**设计原则**

根据任务执行需求区分不同的任务机制，并针对不同执行路径采用相应的上下文管理方式。

**设计体现**

- 普通任务采用标准任务上下文管理机制。
- 高速任务使用独立的任务管理记录及上下文保存区域。
- 利用专用寄存器组减少部分任务切换过程中的现场保存开销。
- 通过统一的调度请求机制衔接任务运行状态变化与调度处理。
- 根据任务类型分别管理栈指针及相关运行记录。

**设计目标**

不要求所有任务都承担相同的上下文保存成本，而是根据任务机制的差异进行针对性优化，使系统能够兼顾常规任务管理能力与对切换开销较敏感的执行场景。

### 4. 以优先级为核心的任务调度

**设计原则**

以任务优先级作为调度决策的重要依据，通过统一的调度入口协调任务状态变化和执行权转移。

**设计体现**

- 区分普通任务与高速任务的执行机制。
- 通过任务状态记录和任务控制块管理任务运行资格。
- 通过调度请求标志及定时器中断触发后续调度处理。
- 支持任务等待、唤醒和延时等状态转换。
- 根据配置及调度机制处理时间片相关行为。

**设计目标**

使任务执行顺序具有明确的调度依据，降低任务间运行关系的复杂度，并为实时应用提供可分析、可测试的任务管理基础。

任务优先级决定调度中的相对执行次序，但系统的实际响应时间仍与中断屏蔽时间、任务切换开销、临界区长度和应用程序执行行为有关。

### 5. 固定内存布局与可预测的资源占用

**设计原则**

优先采用固定规模的数据结构和明确的内存规划，减少运行期间的内存管理复杂度。

**设计体现**

- 任务控制块、资源对象和消息队列采用固定数量的管理结构。
- 内核全局数据按预设偏移组织在指定的 XDATA 区域。
- 通过位图记录任务栈空间的分配状态。
- 按任务类型划分栈指针记录和上下文保存区域。
- 通过编译期配置控制任务数量、资源数量和队列规模。

**设计目标**

让内核的主要内存开销能够通过配置和布局进行核算，便于评估目标芯片的资源容量，降低动态内存管理带来的不确定性。

固定规模也意味着系统容量受到编译期配置限制。任务数量、栈空间及其他内核对象的配置，需要与目标芯片的实际存储资源相匹配。

### 6. 统一的等待与资源管理模型

**设计原则**

通过统一的任务等待状态和资源管理结构，协调不同等待对象与任务状态之间的关系。

**设计体现**

- 使用统一的任务等待接口处理相关等待请求。
- 通过任务控制块记录等待类型、等待对象、等待标志及超时信息。
- 通过资源对象维护资源状态、所有者及等待任务信息。
- 使用等待位图记录普通任务与资源对象之间的等待关系。
- 通过任务唤醒流程更新等待记录和任务运行状态。

**设计目标**

减少不同等待机制之间重复的状态管理逻辑，使任务阻塞、资源释放和任务唤醒具有一致的处理路径，并便于对相关状态转换进行维护和测试。

### 7. 中断处理与任务调度相分离

**设计原则**

明确中断服务程序与任务调度之间的职责边界，避免在中断处理过程中直接执行不适合中断上下文的阻塞操作。

**设计体现**

- 提供专门面向中断场景的接口或处理路径。
- 中断处理期间避免调用需要等待任务运行才能完成的阻塞操作。
- 通过调度请求标志记录需要进一步处理的调度事件。
- 利用中断退出及相应的内核处理流程协调任务切换。
- 根据 8051 的中断优先级与嵌套机制管理中断执行过程。

**设计目标**

使中断服务程序尽量聚焦于事件响应和必要的状态更新，将任务执行权的协调交由内核调度机制处理，从而降低中断路径与任务管理逻辑之间的耦合。

### 8. 临界区与共享状态保护

**设计原则**

对任务和中断可能共同访问的内核状态实施必要的保护，保证关键状态更新过程的一致性。

**设计体现**

- 使用临界区接口保护需要原子化处理的操作。
- 通过嵌套计数或相应状态记录管理临界区进入与退出。
- 在修改任务状态、资源状态和调度相关数据时考虑中断并发访问。
- 在退出保护区域时恢复相应的中断状态。
- 控制关键区域的执行范围，避免不必要地延长中断响应延迟。

**设计目标**

在 8051 的单核执行环境下，协调任务上下文与中断上下文对共享数据的访问，减少因状态更新交错而产生的内核异常。

### 9. 明确的模块边界与接口约束

**设计原则**

按照功能职责组织内核与外围模块，保持模块之间的调用关系清晰，减少重复实现和不必要的交叉依赖。

**设计体现**

- 将任务调度、等待唤醒、资源管理和上下文切换等职责分别组织。
- 通过统一的内部接口连接相关内核模块。
- 将硬件相关实现与上层功能逻辑适当分离。
- 将驱动、通信协议和 Shell 等能力作为外围功能进行组织。
- 通过模块文档说明功能职责、接口用法及相互依赖关系。

**设计目标**

使内核结构更容易理解和维护，同时允许外围功能在不改变核心任务管理机制的情况下持续扩展。

### 10. 以实际工程验证驱动持续优化

**设计原则**

内核优化以可复现的测试、实际硬件表现和问题定位结果为依据，而不是仅以代码长度或理论上的执行效率作为评价标准。

**设计体现**

- 对任务切换、延时精度和中断响应等关键路径进行实测。
- 分别测试不同任务机制及调度触发路径的性能表现。
- 对长时间运行、任务切换和资源状态转换进行压力测试。
- 对发现的问题进行定位、修复和回归验证。
- 将稳定的测试结果、性能数据和使用限制整理为技术文档。

**设计目标**

通过持续测试逐步掌握内核的实际运行特征，使性能改进能够得到验证，缺陷修复能够得到复查，版本演进能够建立在已有工程成果之上。

## 内存设计原则

### 内存分区与访问效率

HRTOS 根据 8051 的存储空间组织方式安排不同类型的数据，兼顾访问效率、容量限制和数据管理需求。

- **DATA**：用于适合直接寻址、需要频繁访问的变量。
- **IDATA**：用于适合间接寻址的内部 RAM 数据。
- **XDATA**：用于存放任务管理数组、上下文记录及其他需要较大空间的数据。

不同存储区的具体使用方式由编译器、芯片型号及内核配置共同决定。内存布局需要与启动代码、栈使用方式及任务切换机制保持一致。

### 栈空间管理

HRTOS 对任务栈和内核使用的栈空间进行规划，并通过相应的栈指针记录和管理数据跟踪栈空间的使用情况。

设计重点包括：

- 根据任务类型设置相应的栈管理结构。
- 采用固定粒度的空间记录管理用户任务栈分配。
- 通过位图记录栈空间的占用状态。
- 在任务创建和清理过程中维护栈空间的分配记录。
- 结合目标芯片的 RAM 容量确定栈空间配置。

栈空间容量应根据任务调用深度、局部变量、中断嵌套和上下文保存需求综合评估。栈检查及异常处理的具体行为取决于相应配置和实现。

### 上下文保存与恢复

上下文管理直接影响任务切换的执行开销，也是 HRTOS 面向 8051 进行优化的重要组成部分。

HRTOS 根据普通任务与高速任务的不同执行机制，分别组织上下文记录及相关栈指针信息。通过合理使用寄存器组和专用保存区域，减少部分执行路径上的现场保存与恢复工作。

上下文保存范围必须满足相应任务机制的运行要求。优化重点是在保证任务状态正确恢复的前提下，控制上下文大小和切换成本。

## API 设计原则

### 接口一致性

内核 API 尽量采用统一的命名风格、参数约定和返回值表达方式，使任务管理、等待、资源同步及通信功能具有相对一致的使用体验。

接口文档应明确说明：

- 函数用途和适用场景。
- 参数含义及有效范围。
- 返回值及其对应的处理结果。
- 是否允许在中断上下文中调用。
- 是否可能阻塞，以及相关超时行为。
- 对任务状态、资源状态或系统调度产生的影响。

### 轻量化接口

接口设计以明确表达操作意图为目标，避免引入与目标平台资源条件不匹配的复杂抽象。

在满足功能需求的前提下，优先采用简洁的参数形式、清晰的状态约定和易于理解的调用方式。对于确实需要额外配置的功能，通过独立参数、配置项或专门接口进行表达。

### 阻塞、非阻塞与超时语义

涉及等待对象或消息队列的接口，应明确区分立即返回、阻塞等待和超时返回等行为。

不同模式需要具有清晰的完成条件和返回语义，使应用程序能够根据任务优先级、响应需求及资源使用方式选择适当的调用形式。

具体支持的模式以各接口的实际定义为准。

## 性能优化原则

### 优化关键执行路径

优先关注对实时响应和任务执行效率影响较大的路径，包括：

- 任务上下文保存与恢复。
- 调度请求的产生和处理。
- 等待任务的唤醒。
- 中断进入、退出及相关状态处理。
- 常见资源操作的快速处理路径。

在满足正确性要求的前提下，通过减少不必要的状态操作、控制临界区长度和优化上下文管理降低执行开销。

### 差异化性能设计

不同任务机制具有不同的执行需求，内核不必为所有任务采用完全相同的处理方式。

HRTOS 通过普通任务与高速任务的差异化管理，针对部分对切换开销敏感的场景进行优化。相关性能应结合实际芯片、编译配置、调度模式和测试条件进行评估。

### 以测量结果评价性能

性能数据应尽可能明确测试平台、时钟频率、编译条件、测试方法和测量范围。

任务切换耗时、中断响应延迟和延时精度属于不同的性能指标，不能相互替代。单项测试结果也不直接等同于整个系统的最坏情况执行时间。

通过持续积累可复现的测试数据，建立内核性能变化的比较依据。

## 可移植性原则

### 硬件相关实现隔离

HRTOS 的内核机制与具体芯片的硬件资源之间需要保持明确的接口关系。定时器配置、寄存器定义、中断向量和底层初始化等内容，应根据目标芯片的特点进行适配。

### 配置驱动的移植

不同 8051 芯片在 RAM 容量、定时器、中断机制、寄存器组及编译器支持方面存在差异。移植时需要综合检查：

- 内部 RAM 与外部 RAM 的容量及地址布局。
- 内核和用户栈的空间分配。
- 定时器时钟及中断周期。
- 中断优先级与嵌套行为。
- 汇编代码和编译器扩展的兼容性。
- 任务数量及其他内核对象的配置限制。

移植的重点不仅是代码能够编译通过，还包括任务切换、时序行为和内存使用能够在目标硬件上正确运行。

## 可靠性与维护原则

### 状态一致性

任务创建、等待、唤醒、删除和清理等操作会涉及多个内核数据结构。相关流程需要保持任务状态、等待信息、栈空间记录和资源等待记录之间的一致性。

### 边界条件处理

内核接口需要针对其定义范围内的参数和状态进行检查，包括任务标识、优先级、栈空间参数、资源索引以及重复注册等情况。

具体检查范围由各接口的设计要求决定。文档应清晰说明参数约束和异常返回行为，帮助应用开发者正确使用接口。

### 回归测试与版本维护

内核功能调整不仅需要验证新增或修改的路径，也应关注对现有功能的影响。

持续维护工作包括：

- 修复已确认的内核缺陷。
- 验证任务状态转换及资源管理流程。
- 复测关键性能指标。
- 检查不同配置下的内存占用。
- 更新 API、模块、移植和测试文档。
- 保持示例程序与公开接口的一致性。

HRTOS 的维护目标是在持续完善功能的同时，尽可能保持已有接口、架构约定和应用代码的稳定性。

## 设计权衡

HRTOS 的架构选择围绕 8051 平台的资源条件与实际应用需求展开，各项设计之间存在相互影响。

| 设计方向 | 主要收益 | 主要约束 |
|---|---|---|
| 轻量化内核 | 控制代码规模和运行开销 | 内核功能需要合理取舍 |
| 固定规模管理结构 | 内存占用清晰、容量便于核算 | 运行容量受编译配置限制 |
| 差异化任务机制 | 针对不同执行路径优化开销 | 需要分别管理相应的上下文 |
| 统一等待模型 | 减少重复状态管理逻辑 | 不同等待对象仍有各自的语义 |
| 8051 原生优化 | 充分利用目标处理器的特点 | 依赖相应的处理器和工具链特性 |
| 中断与调度分离 | 明确中断处理和任务切换的职责 | 任务响应还取决于中断退出及调度条件 |
| 固定内存布局 | 便于分析内核数据占用 | 地址规划需要与配置保持一致 |
| 持续测试与优化 | 以实测结果指导改进 | 测试结论受平台和覆盖范围限制 |

## 后续演进方向

HRTOS 的后续演进以现有内核架构为基础，优先完善已有功能的稳定性、文档质量、测试覆盖和工程集成能力。

### 内核与性能

- 持续验证任务切换、延时和中断响应等关键路径。
- 完善任务栈使用情况及相关异常的检测能力。
- 优化资源等待、唤醒和状态管理流程。
- 在保持现有机制清晰的前提下评估必要的性能改进。

### 功能与生态

- 完善 Shell、Modbus RTU 等现有功能模块的文档与示例。
- 持续丰富驱动接口及常用外围组件。
- 完善模块依赖、内存布局、API 和移植说明。
- 提高示例工程的完整性与可复现性。

### 工程质量

- 扩充不同任务组合及边界条件下的测试。
- 持续整理实际硬件测试数据。
- 加强内核实现、接口文档和示例代码之间的一致性。
- 对已验证稳定的功能保持谨慎修改，降低版本演进对现有应用的影响。

HRTOS 将继续围绕轻量化内核、8051 原生优化和完整工程生态推进建设。设计演进以实际需求、验证结果和长期维护价值为依据，在扩展系统能力的同时，保持内核结构清晰、资源使用可控以及现有功能的稳定性。
