# HRTOS 扩展指南

## 模块介绍

HRTOS 扩展指南用于说明如何在现有系统架构上增加功能、扩展接口、完善外围模块或适配目标硬件。

HRTOS 的扩展工作分为内核扩展、现有模块扩展、公共 API 扩展、外围组件开发和硬件适配等类型。不同类型的扩展涉及不同的内核机制、资源配置及验证要求，应根据实际修改范围确定实施方案。

扩展工作的基本要求是：

- 明确扩展目标及其所属模块。
- 了解相关内核机制和现有接口。
- 评估代码、RAM、XDATA 及任务栈的变化。
- 验证新增功能与现有功能之间的协作关系。
- 同步维护接口说明、使用示例和相关技术文档。

## 扩展类型

### 内核功能扩展

内核扩展涉及任务管理、调度、等待唤醒、资源管理、中断处理、上下文切换及内存管理等机制。

此类修改可能影响多个模块之间的协作关系。实施前应梳理相关数据结构、调用路径和状态转换，并明确修改对任务执行及中断处理的影响。

### 现有模块扩展

现有模块扩展包括为任务管理、资源同步、消息队列、Shell、Modbus RTU 等功能增加接口或完善已有能力。

优先沿用模块现有的接口形式、配置方式和错误处理约定，使新增功能与模块原有能力保持一致。

### 公共 API 扩展

新增公共 API 时，应明确函数的用途、参数、返回值、调用条件和相关状态变化。

如果新接口涉及阻塞等待、任务唤醒或中断上下文，还应说明相应的调用限制和执行行为。

### 外围组件扩展

外围组件包括设备驱动、通信协议及面向应用的辅助功能。

这类功能应尽可能通过公开接口与内核协作，避免在外围模块中重复实现任务调度、等待唤醒等已有内核机制。

### 硬件适配

硬件适配涉及目标芯片的存储空间、定时器、中断向量、寄存器组和编译工具链等内容。

HRTOS 面向 8051 架构设计，适配不同 8051 芯片时，需要验证底层硬件差异与现有上下文管理、内存布局及调度机制的兼容性。若目标平台不再属于 8051 架构，则需要重新评估处理器相关实现，而不仅是替换硬件寄存器定义。

## 扩展实施流程

### 1. 分析现有实现

开始修改前，先确定功能所属模块及其依赖关系。

重点检查：

- 现有功能是否已经提供相应接口。
- 相关模块的数据结构和状态定义。
- 调用路径及模块间依赖。
- 是否涉及任务状态、资源状态或中断状态。
- 现有配置对新增功能的限制。

对于内核功能，应同时关注功能入口、状态更新、异常返回和资源清理等相关流程，避免只修改单个函数而遗漏关联路径。

### 2. 确定扩展方案

根据功能需求确定修改范围，并优先选择影响范围明确的实现方式。

- 能通过外围模块实现的功能，尽量不修改内核。
- 能通过新增接口实现的需求，优先评估新增接口方案。
- 需要修改已有行为时，明确受影响的调用方和兼容性变化。
- 涉及多个模块时，先确定各模块的职责及接口关系。
- 涉及底层机制时，明确其对现有任务切换和中断处理的影响。

### 3. 实现功能

实现过程中应沿用相关模块已有的数据组织方式、接口约定和错误处理模式。

对于涉及共享数据的操作，应考虑任务与中断上下文之间的并发访问；对于涉及等待和唤醒的功能，应保持相关任务状态、等待记录及资源状态之间的一致性。

新增配置项时，应明确默认值、有效范围及其对内存布局和功能行为的影响。

### 4. 完成功能验证

功能实现后，应先验证基本调用流程，再检查边界条件和异常路径。

根据扩展类型，选择适当的功能测试、集成测试、性能测试及长时间运行测试。涉及内核调度或中断机制的修改，还应验证对原有任务执行行为的影响。

### 5. 更新配套资料

扩展完成后，同步更新受到影响的技术资料，包括：

- API 文档及参数说明。
- 模块说明和依赖关系。
- 配置项及内存布局说明。
- 使用示例和测试程序。
- 性能测试结果及适用条件。
- 必要的版本变更记录。

## 各类功能的扩展方法

### 新增 IPC 机制

新增进程间通信机制前，应先确认现有资源同步、消息队列和等待接口是否能够满足需求。

设计时需要明确：

- 通信对象的数据结构及容量。
- 发送、接收、等待或释放操作的语义。
- 是否支持阻塞、非阻塞及超时行为。
- 等待任务的记录方式。
- 任务唤醒及资源状态更新流程。
- 是否需要提供中断上下文接口。

如果新机制能够使用现有等待模型，应优先复用相关任务状态管理和唤醒流程；如果其语义或性能要求不同，则应明确独立实现的必要性及其与现有内核的接口关系。

新增 IPC 后，应重点验证多任务竞争、等待超时、资源释放、任务退出及异常路径。

### 新增系统服务

系统服务用于向应用或其他模块提供公共功能。

扩展时应明确服务的调用接口、内部依赖、初始化要求及资源使用方式。

如果服务需要在系统启动阶段初始化，应确定其初始化时机和依赖顺序；如果服务运行期间维护状态数据，应明确其访问方式及并发保护要求。

系统服务应保持清晰的功能边界，避免将特定应用的业务逻辑直接耦合到内核。

### 扩展现有模块

扩展已有模块时，应先确认原有接口的行为及模块内部的状态管理方式，再确定新增功能的实现位置。

修改过程中应重点检查：

- 原有调用路径是否发生变化。
- 新增状态是否影响原有状态转换。
- 错误返回及资源释放是否完整。
- 新旧接口是否具有一致的使用约定。
- 原有功能是否需要增加回归测试。

如果确实需要改变已有接口或行为，应在相应文档中明确说明变化及其影响范围。

### 新增公共 API

公共 API 应具备明确、稳定的接口定义。

每个新增接口至少需要说明：

| 项目 | 说明内容 |
|---|---|
| 功能 | 接口的用途及适用场景 |
| 参数 | 类型、含义、有效范围及输入要求 |
| 返回值 | 正常结果、失败条件及对应返回值 |
| 调用条件 | 允许的任务或中断上下文 |
| 执行行为 | 是否阻塞、是否触发调度或改变任务状态 |
| 资源影响 | 对内存、任务栈及相关内核对象的影响 |
| 使用示例 | 典型调用方式及必要的错误处理 |

新增 API 后，应同步更新公开头文件、API 文档及相关示例。

### 新增配置项

配置项应具有明确的用途、取值范围和默认行为。

涉及任务数量、资源数量、消息队列容量、栈空间或内存布局的配置，需要检查其与固定数组大小、内存偏移及目标芯片容量之间的关系。

配置变化后，应重新检查受影响的数据占用及功能限制，避免出现配置值与实际存储空间不匹配的情况。

### 适配新的 8051 芯片

适配新芯片时，应先对比现有目标平台与新平台的硬件差异。

重点检查：

- CPU 内核及指令执行特性。
- 内部 RAM、扩展 RAM 及可用地址范围。
- 定时器时钟、计数方式和中断周期。
- 中断向量、优先级和嵌套行为。
- 寄存器组数量及使用方式。
- 编译器、汇编语法和链接配置。
- 内核栈、任务栈及上下文保存区域。

适配完成后，应从基础启动、定时器运行、任务创建、任务切换、中断处理、延时精度和长时间运行等方面逐步验证。

如果硬件差异影响现有上下文切换或内存布局，应针对相关机制进行适配，而不是仅以编译通过作为完成标准。

## 扩展验证

### 功能验证

检查新增功能的正常执行流程、参数边界、失败返回和资源清理行为。

对于具有状态转换的功能，还应检查重复调用、调用顺序变化及异常退出等情况。

### 集成验证

检查新增功能与相关模块之间的协作关系，包括：

- 与任务调度和任务状态管理的协作。
- 与等待、唤醒及资源管理机制的协作。
- 与中断处理和临界区保护的协作。
- 与现有 API 和外围组件的兼容性。
- 与不同配置及目标芯片的适配情况。

### 性能与资源验证

根据功能特点评估其对系统运行的影响，重点包括：

- 代码空间及 RAM、XDATA 占用变化。
- 任务栈和上下文空间需求。
- 关键操作的执行耗时。
- 调度响应和中断处理开销。
- 长时间运行时的稳定性。

性能测试结果应注明测试条件和测量范围。对于尚未进行最坏情况分析的功能，不应仅凭平均耗时或单次测试结果推断其最坏情况执行时间。

### 回归验证

内核或公共接口发生变化后，应重新验证相关原有功能。

回归范围应覆盖受修改影响的模块及其关联路径。对于涉及任务状态、资源管理、上下文切换和中断处理的改动，应重点检查原有执行流程是否受到影响。

## 扩展检查清单

扩展完成后，可根据修改范围逐项检查：

- [ ] 扩展目标及模块边界明确。
- [ ] 已检查现有接口和模块依赖。
- [ ] 新增接口的参数与返回值定义完整。
- [ ] 任务状态、资源状态及异常路径处理完整。
- [ ] 已评估代码空间、RAM、XDATA 和栈空间变化。
- [ ] 已评估调度及中断处理方面的影响。
- [ ] 已完成适用的功能与集成测试。
- [ ] 已完成必要的性能或长时间运行测试。
- [ ] 已检查相关原有功能。
- [ ] 已更新 API 文档、示例及相关模块说明。

## 常见扩展问题

### 修改接口后影响已有应用

修改已有 API 的参数、返回值或执行行为，可能导致原有应用需要调整。

处理方式：优先评估新增接口或兼容性适配方案；如果必须改变原有行为，应明确变更范围，并更新相关文档及示例。

### 新增功能超出芯片资源限制

新增数组、上下文记录或缓冲区，可能使内存布局超出目标芯片的实际容量。

处理方式：在实现阶段核算新增数据的空间需求，并检查静态地址、数组长度、栈空间和其他内核对象之间的关系。

### 任务与中断上下文访问冲突

任务和中断服务程序可能访问相同的状态变量或资源对象。如果缺少适当的同步保护，可能产生状态不一致。

处理方式：明确共享数据的访问路径，依据操作要求使用适当的临界区或内核同步机制，并验证相关中断路径。

### 新增功能影响任务响应

新增操作可能增加临界区长度、任务切换开销或中断处理时间。

处理方式：识别受影响的执行路径，对关键操作进行测量，并根据结果调整实现方式。

### 功能正常但异常路径不完整

功能在常规场景下可以正常运行，并不意味着超时、资源不足、任务退出或重复调用等情况下也能正确处理。

处理方式：根据接口定义补充边界条件和异常路径测试，重点检查状态恢复及资源释放。

## 文档与维护要求

扩展工作完成后，应根据实际修改内容更新相应资料：

- **API 文档**：记录接口用途、参数、返回值及调用限制。
- **模块文档**：说明新增功能、内部职责及模块依赖。
- **内存文档**：更新受影响的数据结构、空间占用和地址布局。
- **配置文档**：记录新增配置项及其影响。
- **示例程序**：提供能够体现接口正确用法的示例。
- **测试记录**：记录测试平台、测试条件、结果和已知限制。
- **版本记录**：说明影响兼容性或改变既有行为的修改。

## 总结

HRTOS 的扩展应以现有内核机制为基础，根据功能类型明确修改范围，并充分考虑 8051 平台的内存约束、任务调度和中断处理特点。

通过合理划分模块职责、复用已有机制、评估资源开销和开展针对性验证，可以在保持内核结构清晰的同时，持续完善 HRTOS 的功能体系与工程支持能力。
