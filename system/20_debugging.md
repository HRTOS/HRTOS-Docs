# HRTOS 调试指南

## 模块介绍

HRTOS 调试指南用于指导开发者定位系统运行过程中出现的异常，涵盖任务创建与运行、任务调度、延时与时间片、中断处理、资源同步、消息通信以及栈空间等方面。

HRTOS 的调试应结合内核运行状态、实际硬件表现和可复现的测试现象进行。对于无法直接观察的问题，可通过串口输出、DEBUG 信息、GPIO 标记及逻辑分析仪等手段逐步缩小排查范围。

调试工作主要包括：

- **现象确认**：明确异常发生的条件、出现频率和影响范围。
- **状态检查**：检查任务状态、等待信息、资源状态及调度相关变量。
- **执行路径分析**：定位异常发生前后的函数调用和中断处理流程。
- **硬件测量**：通过 GPIO、串口及逻辑分析仪观察实际运行行为。
- **问题复现与验证**：通过重复测试确认问题原因，并验证修改结果。

## 调试工具与方法

### 串口输出

串口输出适合观察系统启动过程、接口返回值、关键状态和错误发生的位置。

常见用途包括：

- 检查任务创建及初始化结果。
- 输出关键 API 的返回值。
- 观察任务运行、等待和唤醒的执行顺序。
- 确认定时器及相关配置。
- 记录异常发生前后的关键事件。

调试输出应尽量包含明确的事件标识和必要的状态信息，避免连续输出大量无关内容。

串口发送会消耗 CPU 时间，并可能改变任务调度时序。对于中断响应、任务切换和短时间执行路径，不宜仅依靠串口打印测量耗时。必要时可先记录关键事件，再在非实时敏感路径中统一输出。

### DEBUG 信息

DEBUG 机制用于辅助观察内核运行状态和定位异常。具体可观察的变量、事件和错误信息取决于 HRTOS 实际提供的调试接口及编译配置。

使用 DEBUG 信息时，应重点关注：

- 输出信息对应的执行阶段。
- 相关变量的有效范围和实际含义。
- 调试输出是否改变了执行路径。
- 调试配置是否影响代码大小、内存占用或执行时序。

DEBUG 信息可以帮助缩小排查范围，但不能代替对实际调用流程和状态变化的检查。

### GPIO 与逻辑分析仪

GPIO 标记配合逻辑分析仪，适合观察任务执行区间、中断处理区间和其他需要测量的硬件时序。

基本测量方式如下：

```c
GPIO = 1;

/* 执行需要观察的代码 */

GPIO = 0;
```

逻辑分析仪测得的高电平宽度表示两次 GPIO 操作之间的时间间隔。测量结果还会受到 GPIO 操作开销、函数调用、中断干扰及编译优化等因素影响。

使用时应明确测量起点和终点，并确保测试代码不会改变待测机制的关键行为。

适用场景包括：

- 观察任务切换相关时序。
- 测量指定代码段的执行时间。
- 检查定时器周期及周期性事件。
- 观察中断处理过程。
- 对比不同调度配置下的运行表现。

具体性能测试方法、测试条件和实测数据统一参见《HRTOS 性能测试》相关文档。

## 任务调试

### 任务创建失败

任务创建失败时，首先检查创建接口的返回值，再根据对应错误检查参数及系统配置。

排查内容包括：

- 任务 ID 是否在有效范围内。
- 任务入口地址是否正确。
- 优先级是否符合接口要求。
- 栈空间参数是否有效。
- 是否存在重复注册。
- 当前内存配置是否能够满足栈空间分配要求。
- 系统配置锁是否影响任务创建。

如果创建接口返回成功但任务没有按预期执行，应继续检查任务状态、启动标志、调度条件及任务入口函数，而不是仅凭返回值判断任务已经正常运行。

### 任务创建成功但未运行

建议按以下顺序排查：

1. **确认任务入口**：检查入口地址和初始化过程是否正确。
2. **检查任务状态**：确认任务是否处于可运行状态，是否已经进入等待状态。
3. **检查启动状态**：核对任务启动标志及相关状态记录。
4. **检查优先级**：确认优先级设置是否符合预期，以及是否存在持续运行的更高优先级任务。
5. **检查等待条件**：确认任务是否正在等待延时、资源或其他事件。
6. **检查调度路径**：确认调度请求能够产生，并且后续调度处理正常执行。

如果其他任务能够正常运行，应进一步比较异常任务与正常任务的创建参数、状态记录和执行路径，缩小问题范围。

### 任务运行异常

如果任务能够启动，但出现重复执行、提前退出或运行顺序不符合预期，应检查：

- 任务入口函数及其循环逻辑。
- 任务状态是否被意外修改。
- 等待与唤醒操作的调用顺序。
- 是否存在越界访问或共享变量竞争。
- 是否有中断服务程序修改相关状态。
- 栈空间和上下文保存是否正常。

对间歇性异常，应记录异常发生前的关键事件，并尽量构造能够重复触发问题的最小测试程序。

## 调度调试

### 调度未触发

HRTOS 通过调度请求机制衔接内核状态变化与后续调度处理。调度未按预期发生时，应检查整个触发链路。

排查内容包括：

- 调度请求是否在预期操作中产生。
- `OS_SCHED_REASON` 等调度相关状态是否符合预期。
- Timer0 是否正常运行。
- 中断是否被关闭或长时间屏蔽。
- 当前任务和候选任务的状态是否正确。
- 中断退出及后续调度处理是否正常执行。

应区分“调度请求未产生”“调度请求已产生但未被处理”和“调度已执行但目标任务不符合预期”等不同情况。

### 任务切换顺序异常

任务切换顺序不符合预期时，应结合任务优先级、任务状态和调度模式进行分析。

重点检查：

- 任务优先级配置。
- 当前任务是否满足继续运行的条件。
- 高优先级任务是否处于可运行状态。
- 时间片相关配置及其触发条件。
- 等待任务的唤醒时机。
- 任务上下文保存与恢复过程。

任务切换顺序应依据实际调度规则判断，不能仅凭任务创建顺序或串口输出先后判断调度是否正确。

### 调度异常与性能问题的区别

如果任务执行顺序错误、任务无法恢复运行或调度请求丢失，应优先进行功能性排查。

如果任务顺序正确，但切换耗时、延时精度或响应时间不符合预期，则应进一步使用 GPIO 和逻辑分析仪等手段进行时序测量。

性能测量的具体步骤和指标定义参见《HRTOS 性能测试》相关文档。

## 延时与时间片调试

### 延时不准确

延时行为异常时，应检查：

- Timer0 的时钟及定时器配置。
- 定时器中断是否按照预期运行。
- 延时参数及其单位。
- 等待状态设置与任务唤醒流程。
- 测量起点、终点及测量工具的误差。

还应区分定时器周期、任务延时请求和任务实际恢复执行的时间。任务从等待状态转为可运行状态，并不意味着它一定在同一时刻立即获得 CPU。

### 时间片行为异常

检查时间片行为时，应确认当前使用的调度模式及其相关配置，并观察定时器中断、调度请求和任务切换之间的关系。

如果时间片周期本身不正确，应从定时器配置和中断处理入手；如果时间片周期正常但任务切换行为不符合预期，则应继续检查任务状态及调度条件。

### 时间测量注意事项

时间片周期、任务延时精度、任务切换耗时和中断响应时间属于不同指标。

测量时应明确测试区间，并记录目标芯片、系统时钟、编译配置、调度模式和测试方法。不要将单次测量值直接视为所有运行条件下的固定性能。

## 中断调试

### 中断未响应

中断没有按预期执行时，可按以下顺序排查：

1. 确认对应中断源已正确配置。
2. 检查全局中断及相应中断使能状态。
3. 检查中断向量和入口地址。
4. 检查中断优先级及嵌套配置。
5. 检查中断服务程序是否进入。
6. 检查中断退出流程是否正常完成。

如果中断可以进入但任务没有按预期恢复运行，应继续检查中断处理期间产生的调度请求及中断退出后的调度处理。

### ISR 执行异常

中断服务程序应尽量缩短执行路径，避免执行阻塞操作，并遵循对应接口的中断上下文使用要求。

重点检查：

- 是否调用了不允许在 ISR 中使用的接口。
- 是否存在过长的中断处理过程。
- 是否错误修改任务或资源状态。
- 是否正确处理嵌套中断和退出流程。
- 是否产生了预期的调度请求。

### HRTOS 中断与调度流程

一般任务调度相关的中断处理关系可概括为：

```text
硬件中断发生
      ↓
进入对应中断处理流程
      ↓
执行必要的中断处理
      ↓
更新相关状态或产生调度请求
      ↓
完成中断退出流程
      ↓
内核处理相应调度请求
      ↓
根据任务状态及调度规则决定是否切换任务
```

实际执行路径取决于具体中断类型及相关内核机制。并非所有中断都会触发任务切换，也并非所有中断处理都会唤醒任务。

## 栈与内存调试

### 栈空间异常

栈空间异常可能表现为系统运行不稳定、局部变量异常、返回地址异常或意外复位，但这些现象也可能由其他内存问题引起。

排查时应检查：

- 任务栈的配置和实际分配情况。
- 函数调用层级及局部变量占用。
- 中断嵌套导致的额外栈需求。
- 上下文保存和恢复相关的栈指针记录。
- 任务创建和删除过程中栈空间记录的更新。
- 是否存在数组越界或非法内存访问。

应结合目标芯片的内部 RAM、XDATA 布局及实际栈使用方式分析问题，不宜只根据异常现象直接判定为栈溢出。

### 内存状态异常

如果任务状态、资源状态或其他变量出现非预期变化，应检查相关内存是否被越界访问，以及是否存在多个执行路径同时修改同一数据的问题。

对于固定地址分配的内核数据，还应核对数组长度、地址偏移和占用范围，确认不同数据区域之间不存在意外重叠。

具体地址及空间分配参见《HRTOS 内存布局》。

## IPC 与资源同步调试

### 等待任务无法唤醒

任务等待后没有按预期恢复运行时，应依次检查：

- 等待接口的返回值。
- 任务控制块中的等待类型和等待对象。
- 资源对象的等待记录。
- 释放、通知或超时处理是否实际发生。
- 唤醒流程是否正确更新任务状态。
- 调度请求是否产生并得到后续处理。

如果任务已被标记为可运行，但没有实际执行，应进一步检查调度条件，而不是继续重复执行资源释放操作。

### 资源状态异常

资源同步出现异常时，应检查资源对象的当前状态、所有者信息、等待任务记录以及对应 API 的调用顺序。

重点关注：

- 资源初始化是否正确。
- 获取与释放操作是否匹配。
- 等待任务是否与实际等待对象对应。
- 资源释放时等待记录是否正确更新。
- 任务退出或删除后是否遗留相关资源状态。

具体检查内容应与所使用的资源类型和 API 语义一致。

### 消息队列异常

消息发送或接收行为异常时，应检查：

- 队列初始化及缓冲区配置。
- 队列容量和当前消息数量。
- 消息发送与接收接口的返回值。
- 队列满、队列空等边界条件。
- 发送方与接收方的任务状态。
- 多任务访问时的同步保护。

对于消息内容异常，还应检查消息长度、缓冲区边界以及消息生产和消费双方对数据格式的约定。

## 常见问题排查表

| 问题现象 | 优先检查内容 | 推荐方法 |
|---|---|---|
| 系统无响应 | Timer0、中断状态、调度请求 | 检查关键状态并观察 GPIO |
| 任务未运行 | 创建结果、任务状态、等待条件 | 检查返回值及任务状态记录 |
| 调度顺序异常 | 优先级、运行资格、调度模式 | 记录任务状态变化 |
| 延时不准确 | 定时器配置、唤醒流程 | 逻辑分析仪测量 |
| 中断无响应 | 中断使能、向量、入口及退出流程 | GPIO 标记与状态检查 |
| 任务无法唤醒 | 等待对象、资源记录、唤醒流程 | 跟踪等待与唤醒路径 |
| 资源状态异常 | 获取、释放及清理流程 | 检查资源状态变化 |
| 运行中出现异常数据 | 越界访问、共享状态、栈空间 | 检查内存布局并缩小复现范围 |
| 性能下降 | 调试输出、临界区、切换路径 | 对照测试条件进行时序测量 |

## 调试与性能测试的配合

调试和性能测试的目的不同，但可以互相补充。

调试阶段的重点是确认执行路径、状态变化和异常来源；性能测试阶段的重点是采用明确的测量方法，量化执行耗时、延时精度和响应表现。

建议按照以下顺序进行：

1. 使用 DEBUG 信息或串口输出确认异常现象。
2. 根据任务状态、资源状态和中断流程缩小问题范围。
3. 对涉及时间的异常使用 GPIO 和逻辑分析仪进行测量。
4. 修复问题后重新执行原有复现测试。
5. 对受影响的功能和性能指标进行回归验证。

如果调试输出改变了原有时序，应减少输出或改用硬件标记重新测量。性能数据应记录对应的编译配置、硬件环境及测试条件。

详细性能指标、测试程序及实测结果参见《HRTOS 性能测试》。

## 调试最佳实践

### 分阶段增加系统复杂度

建议先验证基本启动和单任务运行，再逐步加入多任务调度、延时、资源同步、中断及外围模块。

每个阶段都应确认新增功能正常后，再进入下一阶段。这样能够减少多个问题同时出现时的定位难度。

### 保持问题可复现

记录以下信息：

- 目标芯片及硬件环境。
- 系统时钟与编译配置。
- 任务、资源及相关配置参数。
- 触发问题的操作顺序。
- 异常现象及出现条件。
- DEBUG 输出和测量结果。

对于偶发问题，应尽可能保留触发条件，并逐步减少与问题无关的任务和外围功能。

### 修改后进行回归验证

内核代码或配置发生变化后，应重新编译，并针对修改涉及的模块执行相应测试。

涉及任务调度、等待唤醒、资源管理或中断处理的修改，还应检查相关联的执行路径。对于长期运行问题，应根据风险和修改范围安排持续运行测试。

### 区分功能异常与测量误差

观测到的时间变化可能来自真实的内核行为，也可能来自串口输出、GPIO 操作、编译优化或其他中断干扰。

排查时应先确认测量方法和测量区间，再判断是否存在内核功能异常，避免将测量误差误认为系统缺陷。

## 总结

HRTOS 调试应从可复现的现象出发，结合内核状态、实际调用流程和硬件测量逐步定位问题。

串口与 DEBUG 信息适合观察执行过程，任务状态及资源记录有助于分析内核逻辑，GPIO 和逻辑分析仪则适合验证实际时序。对于涉及时间性能的问题，应结合独立的性能测试方法和测试记录进行判断。

通过规范的问题复现、针对性的状态检查和修改后的回归验证，可以逐步提高 HRTOS 问题定位的效率，并为内核的持续维护提供可靠依据。
